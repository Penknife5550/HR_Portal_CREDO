# CLAUDE.md — CREDO HR-Portal

## Projekt

Digitales HR-Portal der CREDO Schultraegergruppe (16 Mandanten). Verwaltet Onboarding, Offboarding, Verbeamtung (PSI), Exit-Interviews und Zeugnisse. Sprache der UI ist Deutsch.

## Tech Stack

- **Framework:** Next.js 15 (App Router, Standalone Output)
- **Frontend:** React 19, TypeScript 5.8, TailwindCSS 4, Radix UI
- **Backend:** Next.js API Routes (`src/app/api/`)
- **Datenbank:** PostgreSQL 16 + Prisma 6 ORM
- **Auth:** JWT (jose/jsonwebtoken) + bcryptjs, Magic Links
- **Verschluesselung:** AES-256-GCM fuer IBAN, SV-Nr, Steuer-ID (`src/lib/encryption.ts`)
- **E-Mail:** Nodemailer/SMTP (primaerer Kanal); Webhooks/n8n nur optionaler Zusatzkanal
- **PDF:** pdfkit, QR-Codes via qrcode
- **Tests:** Jest + ts-jest
- **Linting:** ESLint 9 (next/core-web-vitals)
- **Path Alias:** `@/*` → `src/*`

### Entrypoint (`entrypoint.sh`)

Beim Container-Start passiert automatisch:
1. Pflicht-Umgebungsvariablen pruefen (JWT_SECRET, ENCRYPTION_KEY, BEM_ENCRYPTION_KEY, DATABASE_URL)
2. **Schema-Vergleich** (`prisma migrate diff --exit-code`) — nur wenn es einen Unterschied gibt, geht es weiter mit 3.
3. **Sicherung** (`pg_dump` nach `/backups/vor-schema-abgleich-<Zeitstempel>.sql`) — schlaegt sie fehl, **bricht der Start ab**
4. `prisma db push --skip-generate --accept-data-loss` (Schema synchronisieren)
5. Seed-Check (`prisma/seed-check.js`) — System-Vorlagen sicherstellen, **einmalige Datenmigrationen** ausfuehren, Admin-User anlegen falls noch keiner existiert
6. Next.js Server starten (`node server.js`)

**Warum die Sicherung den Start blockieren darf.** `db push` laeuft mit
`--accept-data-loss`, sonst startet der Container bei jeder neuen
Unique-Constraint nicht mehr. Das Flag heisst aber woertlich, was es tut: Eine in
`schema.prisma` umbenannte Spalte wird als „alte loeschen, neue anlegen"
ausgerollt — unbeaufsichtigt und ohne Rueckfrage. Ohne Migrationsordner gibt es
kein Netz darunter, also ist der `pg_dump` das Netz. Kein Dump, kein Push.

Voraussetzung dafuer: Der Dienst `app` muss `./backups:/backups` einhaengen
(steht in `docker-compose.yml`). Fehlt die Einhaengung, nennt die Fehlermeldung
beim Start genau diese Zeilen. Steuerbar ueber `DB_BACKUP_DIR` (Standard
`/backups`) und `DB_BACKUP_KEEP` (Standard 10 — aeltere eigene Dumps werden
aufgeraeumt, fremde Dateien im Verzeichnis bleiben unangetastet).

Die Einhaengung allein genuegt aber nicht. Der Container laeuft als **uid 1001**
(`nextjs`) mit der Primaergruppe **65533 (`nogroup`)** — das Dockerfile legt zwar
`nodejs` mit gid 1001 an, weist sie dem Benutzer aber nie zu. Bei einem
**Bind-Mount** uebernimmt Docker die Rechte des Host-Verzeichnisses unveraendert
(anders als beim benannten Volume `uploads_data`). Gehoert `./backups` auf dem Host
jemand anderem, scheitert schon das Anlegen der Dump-Datei, und der Start bricht mit
`FATAL: Sicherung ... fehlgeschlagen` ab. Einmal je Server:

```bash
sudo chown 1001 backups
```

Zwei Irrwege: `sudo` beim Docker-Aufruf aendert daran nichts — es regelt den Zugriff
auf den Daemon, nicht die Kennung des Prozesses im Container. Und `chgrp 1001`
greift nicht, weil 1001 die Gruppe `nodejs` ist, die dem Benutzer nicht gehoert.
Vorab pruefbar, ohne etwas zu veraendern:

```bash
sudo docker run --rm --user nextjs --entrypoint sh -v "$PWD/backups:/backups" <image> -c 'id; touch /backups/.schreibtest && rm /backups/.schreibtest && echo OK'
```

### Einmalige Datenmigrationen

Migrationen, die genau einmal laufen duerfen, stehen in `prisma/seed-check.js` und
merken sich ihren Lauf im Modell `SystemMigration` (Tabelle `system_migrations`).

- **Nicht** das `AuditLog` als Merker verwenden: Logs werden aufgeraeumt, und eine
  nicht idempotente Migration, die ein zweites Mal laeuft, verschiebt Daten erneut.
- Merker und Datenaenderung gehoeren in **dieselbe Transaktion** — entweder beides
  oder nichts.
- Fehler werden geloggt, brechen den Start aber nicht ab. Ohne Merker laeuft die
  Migration beim naechsten Start erneut.
- `prisma/seed-check.js` exportiert seine reinen Funktionen und ruft `main()` nur
  hinter `require.main === module` auf — so sind die Regeln ohne Datenbank testbar
  (`src/__tests__/lib/fragebogen-steps.test.ts`).

## Onboarding: zwei Spuren

Fragebogen (Mitarbeiter/in) und Einstellungsmodalitaeten (Fuehrungskraft) laufen seit 09/2026 **parallel, in beliebiger Reihenfolge**. Regeln und Begruendung: `src/lib/onboarding-spuren.ts` (rein, client-sicher) und `src/lib/onboarding-status-abgleich.ts`.

- **Gates an Zeitstempeln, nicht am Status.** Jede Spur hat ihren eigenen Zeitstempel (`submittedAt` bzw. `supervisorSubmittedAt`, Altfall `…Data.isComplete`). Lesen, Schreiben und Absenden eines Links haengen nur daran plus an den HR-Status `REVIEWED`/`COMPLETED`/`EXPIRED` — nie am Stand der anderen Spur (`darfMitarbeiterSchreiben`, `darfVorgesetzteSchreiben`, Gates in `auth.ts`).
- **Status NIE direkt setzen.** Er ist nur noch eine Zusammenfassung (`gesamtStatus`). Jeder Schreiber beansprucht in EINER interaktiven Transaktion zuerst seine Spur per bedingtem `updateMany` (WHERE eigener Zeitstempel `null`, `status notIn HR_STATUS`; count 0 → 409), ruft **danach** `statusAbgleichen(tx, id)` auf und schreibt das AuditLog im selben Commit. Nur so landen zwei gleichzeitige Abgaben korrekt auf „Bereit zur Prüfung". Ausnahmen: HR-PATCH (nur `REVIEWED` bei `bereitZurPruefung`, `COMPLETED` nur aus `REVIEWED`, `EXPIRED`) und der bedingte Wechsel `INVITED → IN_PROGRESS` beim ersten Speichern.
- **`SUPERVISOR_SUBMITTED` heisst „Bereit zur Prüfung"** (beides eingereicht). Solange der Fragebogen offen ist, folgt der Status der Fragebogen-Spur (`INVITED`/`IN_PROGRESS`), auch wenn die Modalitaeten schon da sind.
- **Vorgesetzten-Link** (`POST /api/onboarding/[id]/supervisor-link`) ist wiederholungssicher: gueltiger Link an dieselbe Adresse wird wiederverwendet (keine zweite Mail), andere Adresse **oder abgelaufener Link** = neuer Token (alter tot), nach Abgabe der Modalitaeten 409, Adresse der Person selbst 400 (`gleicheAdresse`, dieselbe Regel wie beim Anlegen). Eine NEUE Adresse muss in `SmtpConfig.allowedRecipientDomains` liegen (leere Liste = keine Einschraenkung), sonst 409 `FUEHRUNGSKRAFT_NICHT_FREIGEGEBEN` vor jedem Schreiben und jeder Mail — `fuehrungskraftAdresseFreigegeben` wie im Offboarding; die schon hinterlegte `supervisorEmail` ist immer erlaubt (Wiederverwenden/Erneuern scheitert nie an der Liste). Die Karte „Vorgesetzten-Link" in der Uebersicht bietet „Neuen Link erzeugen" an, sobald der Link abgelaufen ist oder eine andere Adresse eingetragen wird — sonst blockierte `bereitZurPruefung` (wartet bei jedem Link auf die Modalitaeten) den Vorgang dauerhaft.
- **Anlegen mit beiden Links** (`POST /api/onboarding`, Dialog „Neuer Vorgang"): Vorname/Nachname und E-Mail der Fuehrungskraft sind optional. Der Name steht am Vorgang UND als Vorbelegung in `PersonalData` (Fragebogen zeigt ihn, die Person kann ihn korrigieren; `currentStep` bleibt 0, Status `INVITED`). Mit Fuehrungskraft setzt DIESELBE Transaktion den Link ueber `vorgesetztenLinkSetzen` (`src/lib/onboarding-einladung.ts`) — dieselbe Funktion wie `/supervisor-link`. Die Fuehrungskraft eintragen duerfen nur `HR_EDIT_ROLES` (sonst 403; das Anlegen selbst bleibt bei `PROCESS_CREATE_ROLES`), Mandant per `canAccessProcess` (404 „Organisation nicht gefunden"), danach dieselbe Freigabelisten-Pruefung der Fuehrungskraft wie in `/supervisor-link` (409, ohne bekannte Ausnahmen — nichts angelegt, keine Mail). Die Jahreszahl der Vorgangsnummer und ihr Zaehlbereich kommen aus `vorgangsjahrInBerlin` (`src/lib/vorgangsjahr.ts`, deutsche Zeit statt Container-UTC). Mails erst nach dem Commit; die Antwort meldet `mailVersand` je Link, ein Fehlschlag rollt nichts zurueck (kein automatischer neuer Versuch — HR gibt den Link dann selbst weiter).
- **Erinnerungs-Cron** (`/api/cron/reminders`): Anker der Vorgesetzten-Erinnerung ist `supervisorLinkSentAt`, fuer Bestandslinks ohne diesen Wert Ablauf minus Link-Gueltigkeit, nie vor `invitedAt` (`vorgesetztenLinkErzeugtAm`). Ohne Namen heisst die Person dort und in der Einladung `supervisor-link-created` `MITARBEITER_NEUTRAL`, nie ihre E-Mail-Adresse; die Payload-Bausteine (`vorgesetztenLinkMailFelder`) haben kein Feld `email`, Vorlagen setzen `{{mitarbeiter_name}}` nur nach „für" (Akkusativ). Merker `last…ReminderAt`: bei SENT **und SKIPPED** setzen (Vorlage aus → sonst taeglich Webhook + Protokolleintrag), bei FAILED nicht (naechster Lauf versucht es erneut).
- **Die Abteilungsaufgaben haengen an der Modalitaeten-Spur** (Paket 5, siehe Abschnitt „Abteilungsaufgaben"): „Abteilungen informieren" verlangt eingereichte Modalitaeten samt Vertragsbeginn (`onboardingVersandSperre`), weil die Faelligkeiten daran haengen. Das ist die EINZIGE Stelle, an der eine Funktion auf die andere Spur schaut — und sie liest den Zeitstempel, nicht den Status.
- **Die HR-Uebersicht zeigt beide Spuren nebeneinander** (Paket 2, 09/2026). `ProcessWorkflowStepper` rendert ALLE Schritte mit `status: "active"` (`filter` statt `find`) — frueher fiel der zweite gleichzeitig aktive Schritt aus allen drei Listen und war unsichtbar. Ab zwei aktiven Schritten stehen die Karten in einem Raster, tragen den Chip „Läuft parallel" statt „Aktueller Schritt" und bekommen die Zeile „Schritte X und Y laufen parallel, in beliebiger Reihenfolge"; die Nummern baut die Komponente selbst aus `steps.indexOf`, ein Prop mit festen Zahlen liefe beim naechsten eingeschobenen Schritt auseinander. Bei genau EINEM aktiven Schritt bleibt das Markup unveraendert (daran haengen bestehende Komponententests). Gilt fuer Onboarding **und** Offboarding (dort waren „Rückgaben einsammeln" und „Zeugnis erstellen" neben ihrem Nachbarn nie zu sehen).
- **Die Oberflaeche liest die Spuren-Funktionen, nie `isComplete`.** Die Schrittdaten des Onboardings stehen rein und getestet in `src/app/(portal)/dashboard/[id]/uebersicht-schritte.ts` (`onboardingWorkflowSchritte`, `spurenChips`, `onboardingKurzschritte`) mit eigener enger Eingabeschnittstelle `SchritteStand` — kein Import von `DetailData` (Zirkelbezug), `DetailData` erfuellt sie strukturell. Dort wie in Kopf-Chips, Karten, Reiter-Zaehlern und der Dashboard-Liste entscheiden `mitarbeiterAbgesendet`/`vorgesetzteAbgesendet`/`bereitZurPruefung`; sonst zeigte der Altfall „Zeitstempel gesetzt, `isComplete` fehlt" „in Bearbeitung", waehrend Server und Statuszeile „eingereicht" sagen. Der Modalitaeten-Schritt haengt an KEINER Stelle am Fragebogen (Knopf „Vorgesetzten-Link erstellen" auch bei offenem Fragebogen). Gleichzeitig aktiv sind nur die beiden SPUREN — „Daten prüfen" und „Checkliste abarbeiten" nicht (`checklisteFreigegeben = geprueft`), sonst stuende der Parallel-Satz bei jedem Vorgang und verwaesserte genau die Aussage, um die es geht. „Geprueft" ist `REVIEWED`/`COMPLETED`, **nicht** `istHrStatus`: `EXPIRED` gehoert dort dazu, wurde aber nie geprueft. „Abteilungen informieren…" steht schon VOR der Pruefung schmal in der Zeile des kommenden Schritts „Checkliste abarbeiten" (`WorkflowStep.aktionenAuchKommend`, nur `upcoming`, nie `blocked`) — der Schritt wird dafuer NICHT aktiv. Schreibende Knoepfe der Uebersicht (Vorgesetzten-Link erstellen/erneuern, Abteilungen informieren, Dokumente versenden — im Stepper und in der Karte „Vorgesetzten-Link") gibt es nur mit `HR_EDIT_ROLES` (`SchrittAktionen.darfBearbeiten`, Pflichtfeld); Kopieren und CSV-Export bleiben. Den von aussen geoeffneten Dialog „Abteilungen informieren" zeigt die Karte nur, wenn sie selbst handeln darf (`!nurLesen`).
- **Modalitaeten-Fortschritt nur aus `modalitaetenFortschritt()`** (`src/lib/validations/supervisor-data.ts`, direkt neben `SUP_STEP_CONFIG`). `SupervisorData.currentStep` ist ein **0-basierter Index** (Schema-Default 0 = nie gespeichert); die Anzeige rechnet +1 und kappt am letzten Schritt. `0` heisst „noch nicht begonnen", nicht „Schritt 1 von 5". `formatModalitaetenFortschritt` liefert den fertigen Satz fuer Stepper, Karte „Vorgesetzten-Link" und Dashboard-Liste — drei Anzeigestellen, eine Rechnung, dieselbe Zahl, die auch die Fuehrungskraft sieht.
- **„Bereit zur Prüfung" duerfen die HR-Mails nur mit Beleg sagen.** `questionnaire-completed` und `supervisor-completed` bekommen ihre Aussage ueber die Gegenspur als Merker im Payload, und zwar aus `StatusAbgleich.nach` — dem Stand AUS der Transaktion, nicht aus dem Lesestand davor (der kennt eine gleichzeitige Abgabe der anderen Seite nicht). Fragebogen: genau einer von `modalitaeten_eingereicht` (`nach === "SUPERVISOR_SUBMITTED"`), `modalitaeten_offen` (`SUPERVISOR_PENDING`), `ohne_vorgesetzten_link` (`SUBMITTED`). Modalitaeten: `fragebogen_eingereicht` bzw. `fragebogen_offen`. Fehlt der Abgleich, bleiben die drei leer bzw. gilt „Fragebogen offen" — kein Satz ist besser als ein falscher. Merker sind **Zeichenketten** (`"ja"`/`""`): `renderTemplate` kennt nur „nicht leer", `String(false)` waere nicht leer und der Block bliebe stehen. `{{mitarbeiter_name}}` wird ausdruecklich gesetzt (`mitarbeiterName(...) ?? MITARBEITER_NEUTRAL`), sonst faellt `extractVariables` auf `payload.email` zurueck — die private Adresse im HR-Betreff; im Betreff steht der Name nur nach „für" (Akkusativ). Nach einem Deploy zeigen beide Vorlagen den neuen Text erst nach „Text auf Standard zurücksetzen" (eine DB-Zeile ueberschreibt den Code-Default vollstaendig).
- **Eingangsbestaetigung ueber den normalen Versandweg.** `questionnaire-confirmation-employee` laeuft seit Paket 2 ueber `triggerWebhooks` statt ueber `sendEmail` mit selbst geladener Vorlage; der Text ist unveraendert. Damit wirken Versandprotokoll, Aktiv-Schalter, `recipientTo/Cc/Bcc`, Reply-To, Bedingungsbloecke und die HTML-Maskierung der Namen — und ein Webhook auf dieses Ereignis feuert ab jetzt wirklich (alten n8n-Workflow gegenpruefen, sonst Doppelversand). Den Empfaenger traegt ohne gespeicherte Vorlage der Katalog-Default `{{email}}` (`events.ts`), nicht die Route.
- Die JS-Kopie von `gesamtStatus` in `prisma/seed-check.js` (Heil-Migration `ONBOARDING_PARALLELE_SPUREN_V1`) haelt ein Test gegen die TS-Fassung — beide gemeinsam aendern; dasselbe gilt fuer die Zuordnungstabelle der Migration `ONBOARDING_ABTEILUNGSAUFGABEN_V1`.

## E-Mail-Versand (SMTP primaer)

Genau vier begruendete Ausnahmen rufen `sendEventEmail` direkt: das Dokumentenpaket und die Mails der Nachforderung an die Person (Paket 4) — beide unter „Dokumente & Starterpaket" —, die BEM-Fristenerinnerung `bem-frist-erinnerung` (Abschnitt „Automatische Läufe“) und die individuelle E-Mail `individuelle-mail` (Abschnitt „Individuelle E-Mail aus einem Vorgang“), gelistet in `EVENTS_OHNE_WEBHOOK` (`src/lib/ereignis-liste.ts`)
- **Event-Katalog:** `src/lib/events.ts` — eine Definition je Event (Name, Gruppe, Empfaenger-Default, Beispiel-Payload). Neue Events MUESSEN hier eingetragen werden (Test erzwingt das)
- **Vorlagen:** `EmailTemplate` (DB, Admin-UI) mit Empfaenger-Feldern `recipientTo/Cc/Bcc` (kommagetrennt, `{{variablen}}`-faehig); Code-Defaults in `src/lib/default-email-templates.ts`
- **Antwort-Adresse (Reply-To):** global in `SmtpConfig.replyToEmail`, optional je Vorlage via `EmailTemplate.recipientReplyTo` (`{{variablen}}`-faehig) ueberschreibbar. Aufloesung: Vorlagen-Feld > globaler SMTP-Wert > kein Reply-To
- **Protokoll:** Jeder Versandversuch landet im `EmailLog` (SENT/FAILED/SKIPPED, 90 Tage Aufbewahrung — EINE Stelle: `src/lib/email-log-aufbewahrung.ts`, durchgesetzt vom Lauf „Wartung“ und hoechstens einmal am Tag beim Oeffnen des Versandprotokolls)
- **Mailprotokoll je Vorgang (Reiter „E-Mails“, 09/2026):** `EmailLog.vorgangTyp`/`vorgangId` (Werte wie `AuditLog.processType`) setzt `sendEventEmail` an EINER Stelle aus dem Payload (`vorgangBezugAusPayload`, `src/lib/vorgangs-mails.ts`): `onboardingId` → `offboardingId` → `civilServiceId` → `contractEndId` → `elternzeitId` → `mutterschutzId`, sonst `modul` + `refId` (Unterlagen); wer den Bezug nicht im Payload traegt, gibt ihn als Option `bezug` mit (Dokumentenpaket; die Vertragsverlaengerung gehoert zum Vertragsende-Vorgang). **Nie** bei BEM (`bemFallId` wird bewusst ignoriert — versiegelte Akte, eigenes Kommunikationsprotokoll) und nie beim Test-Versand. Sammelmails ueber mehrere Vorgaenge (`psi-deadline-warning`, `contract-end-unbearbeitet`, `automatischer-lauf-bericht`) bleiben ohne Bezug. Neue Mails landen automatisch im Reiter, sobald ihr Payload die Vorgangs-ID unter einem dieser Schluessel traegt. Route `GET /api/vorgaenge/[modul]/[id]/mails` (nur `HR_EDIT_ROLES`, 404 fuer unbekannt), Oberflaeche `src/components/vorgangs-mails/mail-protokoll.tsx` in Onboarding, Offboarding, Verbeamtung, Vertragsende, Elternzeit und Mutterschutz (Reiter nur fuer `HR_EDIT_ROLES`). Zeilen vor 09/2026 haben keinen Bezug.
- **Variablen:** `renderTemplate` maskiert NICHT (manche Variablen tragen fertiges HTML, z.B. `warnungen_liste_html`). Nur die Namensvariablen (`vorname`, `nachname`, `mitarbeiter_name`, `employeeName`, …) und die Freitexte `kommentar_text`/`aufgabenliste` (Abteilungsaufgaben) bzw. `unterlagenliste`/`unterlage`/`begruendung`/`nachricht` (Paket 4) maskiert `renderEventEmail` im HTML-Teil (`mitMaskiertenNamen`); Betreff und Textteil bleiben roh. `{{ablaufdatum}}` kommt immer aus `formatDatumDE` (deutsche Zeit, TT.MM.JJJJ) — der Container laeuft in UTC.
- **Reporting-API:** Read-Only-Endpunkte unter `/api/reports/*`, Auth per API-Key (`ApiKey`-Modell, Verwaltung in Einstellungen → API-Zugang) oder Portal-Session. Keine sensiblen Felder (IBAN/SV-Nr/Steuer-ID) ausgeben!

## Dokumente & Starterpaket

- **Dokumente-Hub pro Vorgang:** Tab „Dokumente" der Onboarding-Detailseite buendelt Erstellen (Vorlagen + System-Dokumente), Versenden (Starterpaket), Hochgeladenes und PDF-Exporte — mit Prozessschritt-Anzeige („Sie sind hier"). Der **Versand** (Karte „Dokumentenpaket") sitzt seit 04.09.2026 auch im Dokumente-Tab von Offboarding, Verbeamtung und Vertragsverlaengerung; der uebrige Hub (Erstellen/Hochgeladenes/Exporte) bleibt dort Zukunft.
- **Platzhalter-Katalog/Resolver:** Verfuegbare `{variablen}` je Modul liegen client-sicher in `src/lib/placeholder-catalog.ts` (re-exportiert von `doc-template-resolvers.ts`). Der ONBOARDING-Resolver fuellt sie aus Personal-/Vorgesetzten-Daten; sensible Felder (IBAN/SV-Nr/Steuer-ID) werden NUR entschluesselt, wenn die Vorlage sie nutzt (Audit via `sensitiveFields`). Im Vorlagen-Editor zeigt `VariablenKatalog` die Variablen klickbar an.
- **System-Vorlagen:** Editierbare Standard-Vorlagen (z.B. Fuehrungszeugnis-Antrag, `DocumentTemplate.isSystem=true`, Modul ONBOARDING) liegen als Asset unter `public/system-dokumente/` und werden vom Entrypoint (`prisma/seed-check.js`) idempotent geseeded. Das amtliche **Masernschutz-NRW-Formular** wird als statisches PDF (`public/system-dokumente/masernschutz-nrw.pdf`) bereitgestellt — bewusst nicht nachgebaut (Layout-Treue).
- **Dokumentenpaket (Standardpaket + Versand):** Pro Mandant **und Modul** konfigurierbares Set aus zwei Quellen — feste Pool-PDFs (`StarterpaketDokument`, Scope GLOBAL/MANDANT) und Brief-Vorlagen (`DocumentTemplate`), gemeinsam geordnet in `StarterpaketAuswahl` (`dokumentId` ODER `templateId`, plus `modul`). Konfig unter `/mandanten/[id]/starterpaket`.
- **Versand:** `src/lib/dokumentenpaket.ts` (modulneutral) hinter drei Routen — `GET /api/dokumentenpaket` (Zusammenstellung fuer den Dialog), `POST .../pruefen` (Vorpruefung), `POST .../versenden`. Oberflaeche: `dokumentenpaket-section.tsx` + `dokumentenpaket-dialog.tsx`. Verdrahtet sind **alle vier Vorgangsmodule** (Onboarding, Vertragsverlaengerung, Verbeamtung, Offboarding) mit je eigener Mailvorlage; `modulVerdrahtet()` prueft beides, damit kein Modul ohne gelesenes Anschreiben versenden kann. Die abgeloeste `starterpaket.ts` und `POST /api/onboarding/[id]/starterpaket` gibt es nicht mehr.
- **Ausnahme vom Dispatcher-Gebot (mit Begruendung):** `dokumentenpaket.ts` ruft `sendEventEmail` DIREKT statt `triggerWebhooks`. Der Dispatcher reicht weder Anhaenge noch `overrideTo` durch; ihn dafuer zu erweitern hiesse, bis zu 15 MB Personalunterlagen an eine frei konfigurierbare Webhook-URL zu schicken. Die Regel „immer ueber `triggerWebhooks`" gilt unveraendert fuer alle anderen Events — hier ist sie bewusst und begruendet ausgesetzt. Preis: Ein Webhook auf eines der vier `*-sent`-Ereignisse wird angelegt, angezeigt und feuert nie. Das `EmailLog` schreibt `sendEventEmail` selbst, der Protokollteil geht also nicht verloren.
- **Zweite Ausnahme vom Dispatcher-Gebot (Paket 4, mit Begruendung):** Die drei Mails der Nachforderung an die Person — `unterlagen-angefordert`, `unterlagen-erinnerung`, `unterlage-zurueckgewiesen` — gehen DIREKT ueber `sendEventEmail` mit `overrideTo` = Adresse der Nachforderung (`personenMailSenden` in `src/lib/unterlagen-dienst.ts`, auch fuer den taeglichen Lauf). Sie tragen den persoenlichen Upload-Link, und der ist ein Zugang zur Personalakte; `triggerWebhooks` reichte die Payload samt Link an jede frei konfigurierbare Webhook-URL weiter. `overrideTo` verwirft zugleich An/CC/BCC der Vorlage, ein Verteiler dort bekommt den Link also nie. Preis wie oben: Ein Webhook auf diese drei Ereignisse feuert nie (Hinweis in `EVENTS_OHNE_WEBHOOK`; `ereignis-liste.test.ts` haelt die Liste gegen die Quelltexte von `dokumentenpaket.ts` und `unterlagen-dienst.ts`, `unterlagen-dienst.test.ts` prueft, dass `triggerWebhooks` nie mit einem Personen-Event laeuft). Die beiden HR-Mails der Nachforderung laufen normal ueber `triggerWebhooks`. Weitere Ausnahmen gibt es nur mit derselben Begruendung (BEM-Fristen, individuelle E-Mail) — eine neue braucht sie hier.
- **Fuenf Regeln, die beim Aendern gelten muessen:**
  1. **Mandant selbst pruefen.** Die Resolver fallen bei fehlendem Zugriff STILL auf die allgemeinen Platzhalter zurueck — ohne eigene `canAccessProcess`-Pruefung ginge ein leeres Schreiben an eine echte Adresse.
  2. **Sensible Vorlagen brauchen eine Bestaetigung je Versand** (Entscheidung 02.09.2026). Serverseitig erzwungen (409); zusaetzlich bekommt der Resolver die sensiblen Platzhalter ohne Bestaetigung gar nicht erst — die Schranke sitzt im Datenfluss, nicht nur in der Abfrage.
  3. **Nachweis nur nach echtem SENT**, in EINER Transaktion (`DokumentenVersand` + `GeneratedDocument.versandId` + AuditLog + Zeitstempel). Scheitert sie nach dem Versand, bleibt das Ergebnis SENT mit lauter Warnung — ein Fehlschlag wuerde zum Doppelversand verleiten.
  4. **Vorlagen NUR aus `uploads/` und `public/system-dokumente/` lesen** (`leseVorlagenDatei`). `dateipfad` steht in der Datenbank; `readUploadedFile` allein weist System-Vorlagen ab, ungeprueftes `readFile` waere ein Scheunentor.
  5. **Abweichende Empfaengeradressen brauchen eine Freigabe** (`src/lib/empfaenger-allowlist.ts`). Die im Vorgang hinterlegte Adresse ist IMMER erlaubt — beim Onboarding ist eine private Freemail-Adresse der Regelfall, eine Allowlist ueber alle Adressen blockierte also genau ihn. Nur bei Abweichung muss die Domain in `SmtpConfig.allowedRecipientDomains` stehen (Vergleich exakt, nicht per `endsWith`); **leere Liste = keine Einschraenkung** (Auslieferungszustand). Die Pruefung sitzt VOR dem Bauen der Anhaenge — danach ist die Mail samt IBAN unterwegs. Dazu bremst die Versandroute je Benutzerkonto: **10 pro Minute, 60 pro Stunde**, auch fuer abgewiesene Versuche; die Vorpruefung bewusst ohne Limit (sie laeuft nach jeder Aenderung im Dialog und persistiert nichts).
- **Statuscodes:** 404 (Vorgang unbekannt **oder** fremder Mandant — gleicher Text, damit der Code nichts verraet), 409 (leere Auswahl, fehlende Bestaetigung, fehlende Datei, fehlerhafte Vorlage, nicht freigegebene Empfaengeradresse, laufender Versand), 413 (zu gross), 429 (Rate-Limit der Versandroute), 502 (PDF-Dienst oder SMTP). Zentral in `statusFuerFehler()`.
- **Doppelversand-Sperre:** prozesslokal (`laufendeVersendungen`) — ebenso das Rate-Limit der Versandroute (seit Paket 3 gemeinsam mit der individuellen E-Mail in `src/lib/versand-bremse.ts`, Speichernamen unveraendert). Beide tragen nur, solange das Portal als EIN Container laeuft; beim waagerechten Skalieren durch eine gemeinsame Ablage (Datenbank/Redis) ersetzen.

## Individuelle E-Mail aus einem Vorgang (Paket 3, 10/2026)

HR schreibt aus dem Reiter Dokumente eine freie Nachricht mit eigenem Betreff und eigenen Anhaengen (PDF, JPG, PNG, WebP; hoechstens 10 Dateien, zusammen 9 MB) an die Person des Vorgangs — Karte „Individuelle E-Mail“ direkt unter der Paketkarte in Onboarding, Offboarding, Verbeamtung und Vertragsverlaengerung (NICHT Elternzeit, Mutterschutz, BEM, nicht ohne Vorgang). Die Paketkarte bleibt unveraendert und zaehlt nur Pakete. Plan: `docs/module/onboarding/aenderungsplan-2026-09.html`, Abschnitt 3.

- **Wo die Regeln liegen:** rein und client-sicher `src/lib/individuelle-mail.ts` (Grenzen, `MELDUNGEN`, `sendenGesperrtGrund`, `kurzstand`, Statuscodes, Antworttypen, `INDIVIDUELLE_MAIL_AUDIT`/`_LABELS`); Zod in `src/lib/validations/individuelle-mail.ts` (Form der Anfrage in der Route, Inhalt im Dienst; die Nachricht wird VOR der Laengenpruefung auf `\n` normalisiert, weil Browser Formularfelder mit `\r\n` schicken); Server `src/lib/individuelle-mail-dienst.ts` (Vorgang ueber `vorgangsKontextLaden` aus `dokumentenpaket.ts` — derselbe Lader samt `adressen`, eine Adressregel fuer beide Wege; `uebersichtLaden`, `mailSenden`, `anhangLaden`, `individuelleMailsAufraeumen`); Routen `GET|POST /api/individuelle-mail` (POST multipart) und `GET /api/individuelle-mail/anhaenge/[anhangId]`, nur `HR_EDIT_ROLES`; Oberflaeche `src/components/individuelle-mail/` (Karte nur mit `canEdit`). Modelle `IndividuelleMail`/`IndividuelleMailAnhang` (Tabellen `individuelle_mails`, `individuelle_mail_anhaenge`).
- **Sieben Regeln, die beim Aendern gelten muessen:**
  1. **Mandant selbst pruefen**, unbekannt und fremd = dieselbe 404 (auch fuer eine Dialog-Kennung aus einem anderen Vorgang und beim Anhang).
  2. **Adressen:** Die Adressen des Vorgangs sind immer erlaubt (Offboarding: private vorgeschlagen, dienstliche waehlbar), jede andere nur mit Domain in `SmtpConfig.allowedRecipientDomains` (leer = keine Einschraenkung) — geprueft VOR dem Versand, 409.
  3. **Vierte Dispatcher-Ausnahme:** `sendEventEmail(INDIVIDUELLE_MAIL_EVENT, …, { attachments, overrideTo, bezug })`, nie `triggerWebhooks` — dieselbe Begruendung wie beim Dokumentenpaket (Anhaenge vom PC, im Dialog gewaehlte Adresse). `overrideTo` verwirft An/CC/BCC der Vorlage. `ereignis-liste.test.ts` haelt Quelltext und `EVENTS_OHNE_WEBHOOK` gleich.
  4. **Typ aus den Bytes** (`erkenneDateityp`, 415/400), Anzeigename `anzeigeNameBereinigen` (Endung = erkannter Typ), 9 MB Rohbytes, weil die Middleware Portal-Bodys bei 10 MiB still abschneidet (`contentLengthZuGross` vor dem Lesen, 413).
  5. **Nachweis nur nach SENT**, Zeile + Anhaenge + AuditLog (`INDIVIDUELLE_MAIL_SENT` am Vorgang: `onboardingId`/`offboardingId`/`civilServiceId`/`contractEndId`) in EINER Transaktion; im Protokoll nur Laengen, Dateinamen, Groessen, SHA-256, nie der Text. Scheitert die Transaktion nach dem Versand: SENT mit `MELDUNGEN.nachweisFehlt`, Ersatzprotokoll `…_NACHWEIS_FEHLGESCHLAGEN`, abgelegte Dateien geloescht. SKIPPED (Vorlage aus, kein Empfaenger) = 409 `VORLAGE_AUS`, FAILED = 502 mit Grund.
  6. **Einmal je Dialog:** `dialogKennung` (UUID je geoeffnetem Dialog, `@unique`). Zweiter Aufruf mit gespeicherter Kennung → 200 `wiederholt`, kein Versand; waehrend der erste laeuft → 409; nach gescheitertem Nachweis merkt sich der Prozess die Kennung (`versendetOhneNachweis`). Beides prozesslokal wie beim Dokumentenpaket; die Bremse (10/min, 60/h je Konto) teilt sich die Route mit dem Paket (`src/lib/versand-bremse.ts`).
  7. **12 Monate:** Kopien liegen unter `uploads/individuelle-mails/<mailId>/<anhangId>.<ext>` (`dateipfad` relativ zu `uploads/`), gelesen und geloescht NUR unter `ANHANG_WURZEL`. Der Lauf „Aufbewahrung erzeugter Dokumente“ loescht danach Dateien und Nachrichtentext (`inhaltGeloeschtAm`), die Zeile bleibt als Nachweis; Antwortfeld `individuelleMails` (Auswertung in `zeitplaner/bericht.ts`). Ohne eingeschalteten Lauf wird nie geloescht.
- **Mailvorlage** `individuelle-mail` (Gruppe „Allgemein“): Betreff `{{betreff}}`, Text `{{nachricht_html}}`, Block `{{#anhaenge_liste}}`, Signatur `{{absender_name}}` + `{{einrichtung}}`; keine eigene Anrede (die schreibt HR). `betreffOhne` sperrt Nachricht und Anhangliste im Betreff. Maskiert im HTML: `absender_name` (`NAMENS_VARIABLEN`), `betreff` und `anhaenge_liste` (`FREITEXT_VARIABLEN`). Reply-To = `SmtpConfig.replyToEmail`. ## Abteilungsaufgaben (Offboarding und Onboarding)

Checklisten-Aufgaben mit zustaendiger Abteilung (IT, Verwaltung / Sekretariat, Facility, Buchhaltung, DSB, eigene Schluessel) oder der Zustaendigkeit Fuehrungskraft (`VORGESETZTER`) gehen per Link an diese Stelle. Sie hakt ohne Anmeldung ab und kann HR einen Kommentar hinterlassen. HR steuert das ueber die Karte „Aufgaben für Abteilungen" im Tab Checkliste (Paket 1b, 09/2026).

Seit Paket 5 (09/2026) gilt das fuer **beide Module**: Offboarding und Onboarding teilen Kern, Karte, Dialog und Link-Seite. Was sich unterscheidet, steht an EINER Stelle (`AbteilungsModul`, `MODUL_TEXTE` in `abteilungsaufgaben.ts`: Titel, Personen-Label, Bezugsdatum, API-Basis, Seitenpfad); der Onboarding-Teil des Servers liegt in `src/lib/abteilungsaufgaben-onboarding.ts`, die Mailfelder des Vorgangs in `src/lib/onboarding-abteilung-mail.ts`. Die Abweichungen sind unten unter „Onboarding (Paket 5)" aufgezaehlt — sonst gilt alles Folgende unveraendert fuer beide.

- **Wo die Regeln liegen:**
  - `src/lib/abteilungsaufgaben.ts` — rein, client-sicher, ohne Uhr (jede Funktion bekommt `jetzt`), vollstaendig getestet: Empfaenger, Versandentscheidung, Gueltigkeit, Erinnerungsstufen, Mailfelder, Versandbericht und Statuscode, Zeilen der Karte samt erlaubter Aktionen (`abteilungsZeilenBauen`), `MELDUNGEN`, `ABTEILUNGS_AUDIT`/`_LABELS`. Spricht bewusst nicht von „Offboarding", damit Paket 5 sie unveraendert nutzt.
  - `src/lib/abteilungsaufgaben-dienst.ts` (Server) — die vier Aktionen, Uebersicht fuer die Detailseite, taeglicher Lauf, Fristen verschieben, Fuehrungskraft.
  - `src/lib/abteilungsaufgaben-uebergaenge.ts` (Server) — Abhaken und Kommentar ueber den Link und im Portal, Abteilungsstatus, Mails nach dem Commit.
  - Zod in `src/lib/validations/abteilungsaufgaben.ts`. Oberflaeche modulneutral in `src/components/abteilungsaufgaben/` (`abteilungen-karte.tsx`, `aufgaben-seite.tsx`). Client-Code importiert Werte nur aus der reinen Datei, aus `-dienst`/`-uebergaenge` nur `import type`.
- **Routen** sind duenn (Session, Body, EINE Dienstfunktion, Antwort 1:1 — kein zweites Pruefen oder Protokollieren):
  - `POST /api/offboarding/[id]/department-links` — Body leer/`{}` = informieren, sonst `{ aktion: "erneut-senden"|"erinnern"|"link-erneuern", departmentKey }` (Alias `{ action: "remind" }`). Kaputtes JSON = 400, nie „informieren".
  - `GET /api/offboarding/[id]` liefert `abteilungen` (einzige Quelle der Karte), `fuehrungskraft` und `departmentLinks[].url` (vom Server aus APP_URL, nie `window.location`). `PATCH` nimmt Fuehrungskraft und letzten Arbeitstag an.
  - `PATCH /api/offboarding/[id]/checklist/[itemId]` (Portal), oeffentlich `GET /api/offboarding-tasks/[token]` und `PATCH …/[itemId]`, `POST /api/cron/offboarding-reminders` (Handaufruf mit `CRON_SECRET`; taeglich startet ihn der Zeitplaner), `/api/settings/departments[/id]` (`adminHandler`).
  - Onboarding (Paket 5, gleiche Form): `POST /api/onboarding/[id]/abteilungen` (Aktionen) und `GET …/abteilungen` (Uebersicht, schreibt nichts und entschluesselt nichts), `PATCH /api/onboarding/[id]/checklist/[itemId]` (Portal, Antwort `{ item, progress }`), oeffentlich `GET /api/onboarding-tasks/[token]` und `PATCH …/[itemId]`. Die Erinnerungen haengen am bestehenden `POST /api/cron/reminders` (Abschnitt 3), NICHT an einem eigenen Cron. `GET /api/onboarding/[id]` liefert zusaetzlich `abteilungen`, `fuehrungskraft`, `departmentLinks[].url` und je Aufgabe `erledigtVon`/`faelligAm`.
- **Zehn Regeln, die beim Aendern gelten muessen:**
  1. **Token nur einmal.** Ein verschickter Link bleibt gueltig; „Abteilungen informieren" schreibt nur an, wer noch keinen zugestellten Link hat (`versandEntscheidung`). Einen neuen Token gibt es NUR ueber „Link erneuern…" (mit Rueckfrage) oder wenn HR nach einer Adressaenderung „Erneut senden"/„Erinnern" waehlt — beides mit AuditLog `DEPARTMENT_LINK_RENEWED`. Der Cron erzeugt nie einen Token und verlaengert nur mit GLEICHEM Token. Der Link wird VOR dem Versand geschrieben (Anlage per `upsert`), damit keine Mail einen Token enthaelt, den es nicht gibt.
  2. **Nachweis nur bei echtem Versand.** `sentAt` (einmalig) und `lastSentAt` nur bei SENT oder WEBHOOK; FAILED/SKIPPED landen nur in `lastSendStatus`/`lastSendDetail` (nie zugestellt = Zeile rot, sonst Hinweis „Letzte E-Mail nicht zugestellt"). **WEBHOOK-Regel:** SKIPPED wegen deaktivierter Portal-Vorlage (Wortlaut `VORLAGE_DEAKTIVIERT_DETAIL`, ein Test haelt ihn gegen `mailer.ts`) zaehlt als zugestellt, wenn fuer das Event ein aktiver Webhook existiert — `triggerWebhooks` sagt das nicht, der Dienst fragt `webhookConfig.count` selbst. Sonst stuende der Link fuer immer auf „nicht informiert", und jeder Klick feuerte n8n erneut. Scheitert die Mail zu einem NEUEN Token, geht `sentAt` zurueck auf `null` (alter Link tot, neuer nie angekommen); die naechste Mail traegt dann `neuer_link`. Scheitert die Datenbank NACH dem Versand (`ergebnisSpeichern`): 201 mit Warnung `meldungNachweisFehlt` („… bitte nicht erneut senden"), nie 500 — wie Regel 3 beim Dokumentenpaket; im Cron zaehlt das als `errors`.
  3. **409 oder 502** (`httpStatusAusBericht`): 201, sobald eine Mail hinausging; 502 nur, wenn nichts hinausging und ALLE Versuche am Mailserver scheiterten; sonst 409 (fachlich nichts zu tun). Jede Antwort traegt den Bericht je Abteilung mit Grund (`versendet`/`uebersprungen`) und fertige `meldung`/`hinweis` — die Karte erfindet keine Texte und bietet nur Aktionen an, die der Server auch ausfuehrt (`einzelPruefung` ist das Netz darunter). Davor: 403 (nicht `HR_EDIT_ROLES`), 404 (unbekannt ODER fremder Mandant, gleicher Text), 409 bei COMPLETED/CANCELLED und bei laufendem Versand.
  4. **Mails nur bei echtem Wechsel, mit Zeilensperre.** `offboarding-task-completed` (an HR, nur mit An-Feld in der Vorlage) genau einmal je Wechsel offen → erledigt, im Portal nur fuer Aufgaben einer Link-Abteilung bei laufendem Vorgang. `offboarding-department-completed` genau einmal beim Wechsel der Abteilung auf fertig, nur ueber den Link. Dafuer sperrt jede Transaktion ZUERST die Link-Zeile(n) (`linksSperren`: UPDATE, nach Schluessel sortiert), aendert dann die Aufgabe per bedingtem `updateMany`, zaehlt und setzt `allTasksComplete` bedingt — sonst verpassen zwei gleichzeitige Haken auf die letzten beiden Aufgaben den Abschluss. **Sperrreihenfolge ueberall Vorgang → Links → Aufgaben** (`letztenArbeitstagSperren`, `faelligkeitenVerschieben`, Link- und Portal-Weg), sonst droht eine Verklemmung. Mails erst nach dem Commit (`nachDemCommit`: Fehler loggen, Antwort bleibt 200). Nur-Kommentar = keine Mail.
  5. **Erinnerungen** (`erinnerungsStufe`): nur Links mit `sentAt` und offenen Aufgaben, nie bei COMPLETED/CANCELLED. Abstand ab `max(lastSentAt ?? sentAt, lastReminderAt)` (INFO 3, WARNING 2, ESCALATION 5 Tage), Ende 30 Tage nach der spaetesten offenen Faelligkeit. Die Adresse wird je Lauf neu aufgeloest; weicht sie ab oder fehlt sie, ueberspringt der Cron und vermerkt SKIPPED mit Grund am Link (keine Mail, kein Token). Merker `lastReminderAt`/`reminderCount` bei SENT, WEBHOOK und SKIPPED, bei FAILED nicht (naechster Lauf versucht es erneut). Der Knopf „Erinnern" ignoriert Abstand und Ende, nicht aber die **Sperrzeit von 10 Minuten** je Link (gilt auch fuer „Erneut senden"). Der Cron nimmt je Vorgang dieselbe Sperre wie die HR-Aktionen, laesst einen gerade gesperrten Vorgang fuer heute aus und liest danach frisch.
  6. **`VORGESETZTER` geht an die Fuehrungskraft des Vorgangs, nie an `DepartmentConfig`** — ein zentraler Eintrag schickte sonst die Fuehrungsaufgaben aller Einrichtungen an ein Postfach. Quelle: `OffboardingProcess.supervisorEmail/Name` → Zeugnis-Bewertung → Vertragsende (`fuehrungskraftErmitteln`). Eine frei eingetippte Adresse (Neuer Austritt, Tab Übersicht) prueft `fuehrungskraftAdresseFreigegeben` gegen `SmtpConfig.allowedRecipientDomains` (dieselbe Freigabeliste wie beim Dokumentenpaket; leer = keine Einschraenkung, dem Portal bekannte Adressen immer erlaubt) → sonst 409 `FUEHRUNGSKRAFT_NICHT_FREIGEGEBEN`. Fehlt die Fuehrungskraft, bleibt ihre Zeile gelb; die uebrigen Abteilungen werden trotzdem informiert.
  7. **Reservierte Schluessel** `HR`, `MITARBEITER`, `VORGESETZTER` (`RESERVIERTE_ABTEILUNGSSCHLUESSEL`) lassen sich unter Einstellungen → Abteilungen nicht anlegen (400). HR und MITARBEITER arbeiten im Portal und bekommen nie einen Link; Altzeilen bleiben sichtbar und loeschbar, werden aber nie angeschrieben. Sonst gilt der aktive Eintrag der Einrichtung vor dem aktiven zentralen (`empfaengerAufloesen`); eigene Schluessel nach `ABTEILUNGS_SCHLUESSEL_MUSTER`. Der Seed legt Abteilungen nur in einer leeren Tabelle an und ueberschreibt nie gepflegte Adressen.
  8. **Datenzuschnitt der oeffentlichen Seite:** nur die eigenen Aufgaben (Titel, Kategorie, Faelligkeit, Status, eigener Kommentar, seit Paket 5 auch der **Hinweis aus der Vorlage** — `description`, in Mail und Link-Seite sichtbar) plus Name, Vorgangsnummer, Einrichtung, Bezugsdatum (letzter Arbeitstag bzw. Vertragsbeginn) und Gueltigkeit — ohne interne Notiz (`notes`, NIE), Urheber, Fortschritt anderer Abteilungen und Vorgangsstatus (nur `readOnly`). Im Onboarding kommt je Schluessel `zusatz` dazu (siehe unten). COMPLETED = nur lesen (PATCH 409), CANCELLED bzw. Onboarding EXPIRED = 410 mit Hinweis. Zwei Bremsen: je IP (20/min, vor dem Token-Lookup) und je Link (60/min, danach). Der Link-PATCH prueft nach der Sperre erneut, ob die Aufgabe noch seiner Abteilung gehoert (HR kann sie umgehaengt haben → 404).
  9. **Kommentar maskiert, Rohtext `kommentar_text`.** Der Kommentar der Abteilung steht in einem eigenen Feld (`abteilungKommentar`, max. 1000) und ist NIE die interne HR-Notiz. Im Payload ist `kommentar` schon maskiert (`<br>`), der Rohtext `kommentar_text` gehoert nur in Betreff und Textteil. `mailer.ts` maskiert `kommentar_text` und `aufgabenliste` im HTML trotzdem (`FREITEXT_VARIABLEN`), falls ein Admin sie in die HTML-Vorlage schreibt; `renderTemplate` setzt in einem Durchgang ein, Platzhalter im Kommentar bleiben Text. Im AuditLog steht nur die Laenge.
  10. **Prozesslokale Sperren tragen nur bei EINEM Container.** Versandsperre je Vorgang (`laufendeAbteilungsVersendungen`, fuer HR-Aktionen UND Cron, Freigabe im `finally`) und Bremse je Link liegen im Speicher des Prozesses — beim waagerechten Skalieren durch eine gemeinsame Ablage ersetzen (wie beim Dokumentenpaket).
- **Letzter Arbeitstag:** Ein PATCH mit neuem Datum verschiebt in EINER Transaktion die Faelligkeiten aller offenen Aufgaben um dieselbe Spanne und verlaengert betroffene Links (gleicher Token, nur bei laufendem Vorgang). Datum streng `YYYY-MM-DD` mit Rueckprobe (Anlage und PATCH). Schon informierte Abteilungen erfahren davon nichts (bewusst offen).
- **Onboarding (Paket 5) — die acht Unterschiede:**
  1. **EINE Link-Tabelle fuer beide Module.** `OffboardingDepartmentLink` (Map `offboarding_department_links`) traegt `offboardingId?` UND `onboardingId?`, je Modul ein `@@unique([…, departmentKey])`. Der Modellname bleibt bewusst falsch benannt: Umbenennen hiesse Tabelle tauschen, und die laufenden Tokens der informierten Abteilungen haengen daran. Genau EINES der beiden Felder ist gesetzt; Prisma kennt keine CHECK-Constraints, deshalb ist `zuweisungSenden` der einzige Schreiber und jede Abfrage laeuft ueber `LinkBereich`/`linkBereichWhere` (`abteilungsaufgaben-uebergaenge.ts`). Wer eine neue Link-Abfrage schreibt, filtert das Modul mit — `GET /api/offboarding/analytics` zaehlte sonst Onboarding-Links mit (dort steht darum `offboardingId: { not: null }`).
  2. **Ausloeser ist NUR der Knopf von HR.** Kein Versand beim Anlegen, bei der Abgabe der Modalitaeten oder bei einem Statuswechsel — eine Mail an ein externes Postfach faellt nicht als Nebenwirkung an.
  3. **Voraussetzung: eingereichte Modalitaeten** (`onboardingVersandSperre` → 409 mit `grund: "MODALITAETEN_FEHLEN"` / `"VERTRAGSBEGINN_FEHLT"`). Geprueft wird `vorgesetzteAbgesendet` (`supervisorSubmittedAt`, Altfall `supervisorData.isComplete`) UND ein Vertragsbeginn. Ein nur zwischengespeicherter Vertragsbeginn zaehlt NICHT — der Autosave des Modalitaeten-Links schreibt ihn schon vor der Abgabe, und er kann sich noch aendern. Ohne Modalitaeten (z.B. Ehrenamt) bleibt der Knopf gesperrt; ein Ersatzdatum gibt es nicht (Entscheidung 22.09.2026). Die Karte zeigt den Grund im Klartext und die Zeilen trotzdem als Vorschau.
  4. **Faelligkeiten genau einmal** (`faelligkeitenSetzen`): Vertragsbeginn + `relativeDueDays` (Kopie von `ChecklistTemplateItem.defaultDueDays`), `WHERE dueDate: null AND relativeDueDays != null`. Angestossen nach dem Commit der Modalitaeten-Abgabe (`POST /api/modalitaeten/[token]`, Fehler wird nur geloggt) und sonst beim ersten „Abteilungen informieren". Nachgerechnet wird nie — nach der Abgabe ist der Vertragsbeginn eingefroren (anders als der letzte Arbeitstag im Offboarding). Ohne Tagesangabe bleibt die Aufgabe **ohne** Faelligkeit und loest keine Erinnerung aus (null heisst nicht 0). Setzt der Portal-PATCH `dueDate: null`, raeumt er `relativeDueDays` mit ab — sonst stellte der naechste Lauf die von Hand geloeschte Frist wieder her.
  5. **`assignee` SELBST traegt den Schluessel** (kein zweites Feld): Die Migration `ONBOARDING_ABTEILUNGSAUFGABEN_V1` in `prisma/seed-check.js` stellt Freitext („Verwaltung", „Vorgesetzter") einmalig auf Schluessel um; unbekannte Texte bleiben stehen, gehen NIE per Link hinaus (`istLinkAbteilung` verlangt Schluesselform) und stehen in `unbekannteZustaendigkeiten`, damit sie nicht einfach fehlen. Die Zuordnungstabelle gibt es zweimal (TS `abteilungAusZustaendigkeit`, JS-Kopie in `seed-check.js`) — ein Test haelt sie gegeneinander, beide gemeinsam aendern. **Angezeigt wird nie der Rohschluessel:** Name aus `abteilungen.zeilen`, sonst `abteilungLabel()`; im Checklisten-Editor und im PDF-Export zusaetzlich die Namen selbst angelegter Schluessel aus `DepartmentConfig` (`abteilungLabel` ist rein und darf die Einstellungen nicht kennen).
  6. **Datenzuschnitt je Schluessel** (`ONBOARDING_ZUSATZFELDER`, `zusatzWerte`, `sichtbarkeitsHinweis`): IT sieht zusaetzlich Stellenbezeichnung, Betriebsstaette und Adresse der Fuehrungskraft; VERWALTUNG/FACILITY Betriebsstaette und Adresse der Fuehrungskraft; DSB die Stellenbezeichnung; VORGESETZTER Stellenbezeichnung und Betriebsstaette; BUCHHALTUNG und eigene Schluessel nichts. Nicht erlaubte Felder fehlen im Payload GANZ (auch nicht als `""`) — so steht in keinem Webhook mehr als erlaubt. Angaben aus dem Personalfragebogen, die private Adresse der Person und der Fortschritt anderer Abteilungen gehen an niemanden. Dialog und Payload lesen dieselbe Tabelle; zwei Texte ueber dieselbe Sache gehen auseinander, einer nicht.
  7. **Vier eigene Events** (Gruppe „Onboarding", `wired: true`): `onboarding-department-assigned`, `onboarding-department-reminder`, `onboarding-task-completed` (nur ueber den Link — das HR-Haekchen im Portal loest im Onboarding NICHTS aus; `defaultRecipients.to` ist leer, ohne An-Feld in der Vorlage also SKIPPED), `onboarding-department-completed`. Kein `token` im Payload (anders als im Offboarding, bewusst). Ohne die Vorlagen in `default-email-templates.ts` meldet `sendEventEmail` SKIPPED → `sentAt` bleibt null → 409; der Versand haengt also an den Vorlagen.
  8. **Erinnerungen im BESTEHENDEN Cron.** `onboardingErinnerungenSenden` laeuft als Abschnitt 3 in `POST /api/cron/reminders`; die Antwort bekommt `departmentReminders`, `total` bleibt Mitarbeiter + Vorgesetzte (Abwaertskompatibilitaet der Antwort; taeglich startet den Lauf der Zeitplaner). Ein Fehler dort laesst Abschnitt 1 und 2 unberuehrt.
- **Checklisten-Vorlagen (Quelle der Zustaendigkeit):** `ChecklistTemplateItem` traegt `defaultAssignee` (Schluessel, Auswahl statt Freitext), `defaultDueDays` und seit Paket 5 `description` (Hinweis fuer die zustaendige Stelle, max. 500). `POST /api/onboarding` kopiert alle drei in die Aufgabe (`assignee`, `relativeDueDays`, `description`), `dueDate` bleibt null. **`PUT /api/checklisten/[id]`** ersetzt Metadaten und Punkte in EINER Transaktion und behaelt vorhandene Punkt-IDs (`ChecklistItem.templateItemId` laufender Vorgaenge zeigte sonst ins Leere); der Editor nutzt nur noch diesen Weg und verwirft keinen unvollstaendigen Punkt mehr still. **Reihenfolge (10/2026):** Im Editor laesst sich die Liste per Ziehen am Griff, Pfeilen und „+ Punkt darunter“ ordnen; gespeichert wird `orderIndex` = Position in der flachen Liste. Alle Leser der Vorgangs-Checklisten (Detailrouten, Checklist-Routen, Abteilungsaufgaben, Link-Seite) sortieren deshalb `orderIndex` ZUERST und die Kategorie nur bei Gleichstand; gruppiert wird nach erstem Auftreten. Wer eine neue Lesestelle baut, sortiert nicht wieder alphabetisch nach Kategorie — sonst gilt die Reihenfolge der Vorlage nur innerhalb einer Kategorie („Dokumente“ stuende vor „Vor Arbeitsbeginn“). Bestehende Vorgaenge behalten ihre kopierten Positionen. Beginnt der Vorlagenname mit „Offboarding:", setzen POST, PUT und PATCH `questionnaireType` auf null — sonst zoege `POST /api/onboarding` (sucht `questionnaireType` + `isActive`) eine Austritts-Checkliste in einen Einstellungsvorgang.
- **Mailvorlagen:** `offboarding-department-assigned` (Aufgabenliste, Gueltigkeit, `erneut_gesendet`, `neuer_link`), `offboarding-reminder` (Knopf und Cron gleicher Aufbau; Stufen ueber die Merker `ist_info`/`ist_warnung`/`ist_eskalation`/`ist_ueberfaellig`, weil `renderTemplate` nicht vergleichen kann), `offboarding-task-completed` (`erledigt_ueber`, Kommentar), `offboarding-department-completed` (Text unveraendert, `ist_fuehrungskraft` im Payload). Alle alten Payload-Felder bleiben fuer Webhook-Abnehmer. Nach einem Deploy mit geaendertem Text: „Text auf Standard zurücksetzen". Im Onboarding dieselbe Reihe mit eigenen Texten („Dienstbeginn" statt „Austrittsdatum"). Dort steht `{{abteilung}}` NIE im Satzsubjekt oder hinter einer artikellosen Praeposition, sondern in Klammern („zuständig: {{abteilung}}") oder in einer Label-Zeile — der Wert ist ein frei gepflegter Anzeigename („Datenschutzbeauftragte/r", „Verwaltung / Sekretariat"), an dem jeder vorformulierte Satz mit Artikel zerbricht; der Empfaenger wird stattdessen mit „Sie" angesprochen. `FREITEXT_VARIABLEN` in `mailer.ts` maskiert zusaetzlich `stellenbezeichnung`, `betriebsstaette` und `aufgabe` im HTML-Teil (getippt ueber den Modalitaeten-Link bzw. aus einer Vorlage).

## Unterlagen nachfordern (Paket 4)

HR fordert fehlende oder verlaengerte Nachweise ueber einen persoenlichen Link an. Die Person laedt je Unterlage eine oder mehrere Dateien hoch (PDF, JPG, PNG, WebP; je Datei hoechstens 9,5 MB) und klickt „Unterlagen übermitteln"; HR prueft jede Unterlage einzeln (Annehmen, Zurückweisen, Entfällt, Annahme zurücknehmen). Erst eine **angenommene** Unterlage wird zum `Document` des Vorgangs. Stufe 1 (09/2026, seit 26.09.2026 auf `main`, noch nicht deployt) deckt nur das Onboarding ab: Karte „Unterlagen nachfordern" im Reiter Dokumente, Knoepfe im Kasten „Offene Nachweise" und im Warnbalken, Pille am Reiter, Kurzstand in der „Status-Übersicht". Spezifikation samt Abweichungen: `docs/module/onboarding/paket4-feinplanung.md` (Abschnitt 18), Deploy: `docs/historie/deploy-paket4-stufe1.md`, Stand und offene Punkte (weitere DSB-Themen, n8n, Caddy-Logging V-9 — Entscheidung vertagt, Stufe 2): `docs/historie/paket4-stufe1-uebergabe.md` — Einstieg und Arbeitsliste für die nächste Sitzung in Abschnitt 0.

- **Wo die Regeln liegen:**
  - Rein, client-sicher, ohne Uhr (jede Funktion bekommt `heute`/`jetzt`), vollstaendig getestet: `src/lib/unterlagen.ts` (Konstanten, Zustaende und Uebergaenge, `vollstaendigMerker`, `linkGueltig`, `erlaubteAktionen`, `uebersichtBauen`, `erinnerungFaellig`, `laufWaechter`, Pille, `MELDUNGEN`, `aktionsTexte`, `UNTERLAGEN_AUDIT`/`_LABELS`), `src/lib/unterlagen-fristen.ts` (was der Lauf je Nachforderung tut, `laufPlanen` — dieselbe Planung fuer `dryRun`), `src/lib/unterlagen-mail.ts` (Payloads, neutrale Nennung), `src/lib/kalendertag.ts` (Berliner Kalendertage), Zod in `src/lib/validations/unterlagen.ts`. `unterlagen.ts` ist modulneutral und kennt den Vorgangsstatus nur als `vorgangEingestellt`.
  - Server: `unterlagen-dienst.ts` (HR-Aktionen, Uebersicht, Datei oeffnen, Mails, Mail-Bremse, Sperre je Vorgang, Register `BAUSTEINE`), `unterlagen-onboarding.ts` (Baustein ONBOARDING: `verfuegbar`, Sperre, Empfaenger, Auswahl, Uebernahme als `Document`), `unterlagen-upload.ts` (oeffentliche API, Bremsen, `oeffentlicheAntwort`), `unterlagen-dateien.ts` (alles auf der Platte), `unterlagen-lauf.ts` (taeglicher Lauf). Dazu `content-security-policy.ts`, `nach-der-antwort.ts` (`after()`), `fehler-kennung.ts` (`fehlerKennung`: in die Konsole nur `code ?? name`, EINE Fassung fuer Dienste, Routen, Lauf und `after()`) und in `file-upload.ts` Typerkennung, PDF-Merkmale, Anzeigename, `pfadInWurzeln`, `zielVerzeichnisPruefen`, `dateiLoeschen`, `leseBodyBegrenzt`.
  - Oberflaeche modulneutral in `src/components/unterlagen/` (`nachforderung-karte.tsx`, `nachforderung-dialog.tsx`, `pruef-dialoge.tsx`, `dialog-rahmen.tsx`, `upload-seite.tsx`; gemeinsame Client-Helfer — Aufruf, Meldungen, Adressvergleich und -format (`adressFormatFehler`), der heutige Tag der drei Frist-Dialoge (`dialogHeute`: Tag des Servers, nie frueher als im Browser) — in `aktionen.ts`, damit keine Komponente eine andere nur wegen eines Helfers importiert), Seite `src/app/unterlagen/[token]/`. Karte und Dialoge rechnen nichts selbst: Zeilen, Pillen, Texte, Aktionen, Datei-URLs und die Routenbasis (`apiBasis`, nur mit Bearbeitungsrecht; keine zweite Tabelle im Client) kommen fertig aus `uebersichtBauen`. Client-Code importiert Werte nur aus den reinen Dateien, aus den Serverdateien nur `import type`.
- **Routen** sind duenn (Sitzung, Body, EINE Dienstfunktion, Antwort 1:1). Kaputtes JSON oder fehlende `aktion` = 400, nie eine Standardaktion (`jsonKoerperPruefen`):
  - HR (`HR_EDIT_ROLES`, sonst 403; Mandant per `canAccessProcess`, unbekannt ODER fremd = 404 mit gleichem Text): `POST /api/onboarding/[id]/unterlagen` mit `aktion` `anfordern`|`ergaenzen`|`frist-aendern`|`erneut-senden`|`zurueckziehen`; `POST …/unterlagen/positionen/[positionId]` mit `annehmen`|`zurueckweisen`|`entfaellt`|`annahme-zuruecknehmen`; `GET …/unterlagen/dateien/[dateiId]` (HR oeffnet eine uebermittelte Datei). Keine eigene Uebersicht: `GET /api/onboarding/[id]` liefert `unterlagen` an `PORTAL_ROLES`; Dateinamen, Datei-URLs, Aktionen, `apiBasis` und Dialogdaten nur mit `HR_EDIT_ROLES`, Entwuerfe nie.
  - Oeffentlich (nur Token): `GET /api/unterlagen/[token]`, `POST …/positionen/[positionId]/dateien` (multipart, genau ein `datei`), `DELETE …/dateien/[dateiId]` (nur Entwuerfe), `PATCH …/positionen/[positionId]` („Gültig bis"), `POST …/uebermitteln`.
  - `POST /api/cron/unterlagen-fristen[?dryRun=1]` (Handaufruf mit Bearer `CRON_SECRET`; taeglich startet ihn der Zeitplaner, zeitkonstant verglichen; 409, solange ein Lauf arbeitet).
- **Zwoelf Regeln, die beim Aendern gelten muessen:**
  1. **Tabellen und Zustaende.** Vier Tabellen: `unterlagen_nachforderungen` (Kopf, `LAUFEND` → `ERLEDIGT`|`ZURUECKGEZOGEN`), `unterlagen_positionen` (`ANGEFORDERT`/`EINGEREICHT`/`ANGENOMMEN`/`ZURUECKGEWIESEN`/`ENTFAELLT`), `unterlagen_dateien` (`ENTWURF`/`EINGEREICHT`/`ANGENOMMEN`/`ZURUECKGEWIESEN`/`VERWORFEN`), `unterlagen_links` (zugleich der Mailverlauf). Zustaende sind Strings, keine Enums — `db push --accept-data-loss` spielte einen umbenannten Enum-Wert still aus. Der Vorgang haengt per nullbarem FK je Modul (Cascade) plus Spalte `modul`; genau eines ist gesetzt, einziger Schreiber des Kopfes ist `nachforderungAnlegen`, jede Abfrage laeuft ueber `bereichWhere` des Bausteins. **Hoechstens eine laufende Nachforderung je Vorgang:** `laufendSchluessel` = `"<MODUL>:<vorgangId>"` `@unique`, ausserhalb von `LAUFEND` `null` (mehrere NULL kollidieren nicht) — Doppelklick, gleichzeitiges Anlegen und Wiederoeffnen neben einer neuen enden als P2002 → 409. `ERLEDIGT` → `LAUFEND` gibt es nur ueber „Annahme zurücknehmen" (hoechstens 30 Tage nach der Annahme, keine andere laufend, nie nach `ZURUECKGEZOGEN`): das `Document` wird geloescht, die Datei zurueckgeholt. Kinder haengen am Vorgang bzw. am Token (`{ id, nachforderungId: link.nachforderungId }`); eine fremde ID ergibt dieselbe 404 wie eine unbekannte. Die Frist ist ein Kalendertag (`@db.Date`), morgen bis heute + 90, jederzeit verlaengerbar; „Frist ändern" mit derselben Frist = 409 (`FRIST_UNVERAENDERT`, dafuer gibt es „Link erneut senden").
  2. **Links nur als Hash, mit eigenem Ende.** Jede Mail an die Person bekommt einen neuen Token (`randomUUID`); gespeichert werden nur `hashToken()` (`tokenHash @unique`) und `gueltigBis`. Gueltig bis `min(link.gueltigBis, Frist + 14)` einschliesslich, in Berliner Kalendertagen; eine Friständerung schreibt nur noch lebende Links fort — ein abgelaufener lebt nie wieder auf. HR sieht den Link nie (kein „Link kopieren"), ein GET schreibt nichts (Mailscanner verbrauchen nichts). Aeltere Links bleiben gueltig, **ausser** bei Adresswechsel (`entwertetGrund = ADRESSE`, sofort in der Transaktion des neuen Links → 404, die falsche Empfaengerin erfaehrt nichts; ihre Entwuerfe sieht die neue Adresse nicht — Grenze `entwuerfeAb`/`eigenerEntwurf` in `unterlagen.ts`, `entwertetAm` und `hochgeladenAm` beide UNTER der Zeilensperre der Nachforderung gestempelt, `zeitpunktUnterSperre`) oder bei „Frühere Links sperren" (`GESPERRT` erst NACH SENT der neuen Mail → 410 „durch einen neueren ersetzt"; der Wunsch steht als `fruehereSperren` am neuen Link und gilt auch, wenn erst der Lauf die Mail nachholt). Nie entwerten bei FAILED/SKIPPED — ein SMTP-Timeout meldet FAILED auch bei angenommener Mail. Linkende, zurueckgezogen, Vorgang `EXPIRED` = 410 ohne Name, Einrichtung und Vorgangsnummer; `ERLEDIGT` = 200 mit `readOnly`. „Link erneut senden" nach der Frist geht bis zum Linkende (Mail mit `frist_verstrichen`), danach 409 „Bitte zuerst die Frist ändern".
  3. **Mails an die Person NUR per `sendEventEmail` mit `overrideTo`, NIE ueber `triggerWebhooks`** (zweite Ausnahme, siehe „Dokumente & Starterpaket"). Die Link-Zeile entsteht VOR dem Versand in der Transaktion der Aktion (`mailStatus AUSSTEHEND`) und traegt danach das Ergebnis; FAILED (oder `AUSSTEHEND` aelter als 1 h) holt der Lauf nach, hoechstens 3-mal, mit neuem Link und `ist_nachgeholt`; SKIPPED nie. Einen `AUSSTEHEND`-Link aelter als 1 h gleicht der Lauf VOR der Planung mit dem `EmailLog` ab (`ergebnisseKlaeren`: SENT desselben Ereignisses an dieselbe Adresse im Fenster des Links → SENT nachgetragen, keine zweite Mail; sonst FAILED „kein Ergebnis", auch bei Erinnerungen). „(neu)" beim Nachholen einer Ergaenzung bezieht sich auf den Link von HR, mit dem die Kette begann. Deshalb prueft jede Aktion mit Personen-Mail die gespeicherte Vorlage VORHER (`personenVorlagePruefen`: fehlt, deaktiviert, kein `{{link}}` im HTML, gesperrter Betreff → 409 ohne jede Aenderung) — sonst liefe eine Nachforderung, von der die Person nie erfaehrt. Statuscodes (EP-11): Anfordern, Ergaenzen, Frist aendern und Zurueckweisen antworten 2xx, sobald der Zustand gespeichert ist; das Mailergebnis steht in `mail`, bei FAILED/SKIPPED mit `warnung` (eine nie zugestellte Aufforderung zeigt die Oberflaeche rot). Nur „erneut senden" antwortet 201/502/409, weil die Mail dort die Aktion ist. Mail versendet, Speichern gescheitert: einmal wiederholen, dann 2xx mit „versendet, bitte nicht erneut senden", nie 500/502 (N2, wie Regel 2 der Abteilungsaufgaben) — der Lauf traegt das Ergebnis dann aus dem Versandprotokoll nach; fehlt auch dort der Eintrag, holt er die Mail nach.
  4. **HR-Mails ueber `triggerWebhooks`** (`unterlagen-vollstaendig`, `unterlagen-frist-verstrichen`): An `{{anfordernde_email}}` (Konto inaktiv oder geloescht → HR-Postfach), CC `{{hr_postfach}}` = `SmtpConfig.replyToEmail`, bei gleicher Adresse geleert (der Mailer entdoppelt nur innerhalb eines Feldes). Die Payload traegt weder Link noch Adresse der Person noch Namen von Unterlagen — nur deshalb duerfen sie an Webhooks. `portalLink` fuehrt auf `/vorgaenge/onboarding/<id>?tab=dokumente` (`vorgangPfad`, die Detailseite versteht `?tab=` mit deutschen Aliassen). „Vollständig" loest nur die Uebermittlung der Person aus, nie eine HR-Aktion (`vollstaendigMerker`, feste Tabelle); gemeldet wird ueber einen **bedingten Anspruch** (`updateMany … vollstaendigSeit: gelesen, vollstaendigGemeldetAm: gelesen`, dazu `hrMeldungStatus = AUSSTEHEND`), bei FAILED zurueckgesetzt. Ein Anspruch, der nach ueber einer Stunde noch AUSSTEHEND steht (Prozess starb zwischen Anspruch und Versand, etwa `after()` waehrend eines Neustarts), ist verwaist (`vollstaendigAnspruchVerwaist`) — der Lauf uebernimmt ihn bedingt auf genau diesen Zeitstempel und holt die Mail nach. `POST /api/unterlagen/[token]/uebermitteln` (`unterlagenUebermitteln`) schickt sie nach der Antwort (`nachDerAntwort` um `after()`), das Hochladen einer Datei nie; der Lauf holt Ausfaelle nach. „Frist verstrichen" einmal je Fristwert (`fristGemeldetFuer`), nur solange etwas auf die Person wartet. Letztes Ergebnis in `hrMeldungStatus`/`hrMeldungDetail` (nur Grundcode, nie Rohtext des Mailers); die Karte zeigt „HR-Meldung nicht zugestellt (kein Empfänger)", die Versand-Ampel warnt, wenn eine Vorlage `{{hr_postfach}}` nutzt und die Antwortadresse leer ist.
  5. **Betreff ohne Unterlagen und ohne Link, sensible Unterlagen neutral.** `EventDefinition.betreffOhne` sperrt `unterlage`, `unterlagenliste(_html)`, `begruendung(_html)`, `nachricht(_html)`, `link`, `magicLink`, `magicUrl` im Betreff aller fuenf Events — das `EmailLog` speichert Betreffzeilen 90 Tage. `PUT /api/settings/email-templates/[id]` weist sie mit 400 ab, ebenso ineinander geschachtelte Marker (`betreffMitVerschachteltenMarkern`), aus denen der Renderer erst ein `{{link}}` zusammensetzte. **Sensible Arten** (`SENSIBLE_DOKUMENTTYPEN`: Masernschutz, SB-Ausweis, Fuehrungszeugnis, Aufenthaltstitel, Arbeitserlaubnis; beim Anlegen nach `position.sensibel` kopiert) nennt eine Mail nur als „Eine vertrauliche Unterlage – Einzelheiten sehen Sie nach dem Öffnen des Links", bei ihrer Zurueckweisung bleiben `unterlage` und `begruendung` leer — beides steht nur auf der Upload-Seite (E-2: Freemail-Anbieter lesen mit, der Aufenthaltsstatus verraet die Herkunft). Anforderbar sind sie nur nach `sensibelAnforderbar` (Pflicht oder schon vorhanden; SB-Ausweis nur mit `severelyDisabled`; Fuehrungszeugnis bei `KITA` gesperrt bis zur Entscheidung des DSB), geprueft auf dem Server (409) — auch bei der Artwahl beim Annehmen einer freien Zeile. Freitexte stehen roh (Betreff, Textteil) und maskiert (`…_html`); `FREITEXT_VARIABLEN` maskiert die Rohfelder im HTML zusaetzlich, `angefordert_von` steht in `NAMENS_VARIABLEN`.
  6. **Bremsen und Kontingente.** Mails an die Person durch HR: hoechstens 6 je Stunde und 20 je Tag **je Vorgang** ueber alle seine Nachforderungen (je Nachforderung setzte „Zurückziehen" + „Anfordern" das Budget zurueck), gezaehlt aus `unterlagen_links` mit gesetztem `erstelltVonId` (uebersteht Neustarts, der Lauf zaehlt nicht mit), darueber 429 mit `Retry-After`; „Link erneut senden" zusaetzlich 10 Minuten nach der letzten zugestellten ERNEUT-Mail. Oeffentlich: IP 20/min (`tokenRateLimiter`, VOR dem Token-Lookup), Hochladen 30 je 10 Minuten und die uebrigen Schreibwege 60/min je NACHFORDERUNG, nicht je Link (jede Mail bringt einen neuen Link, ein Schluessel je Link vervielfachte das Budget). Kontingente: 30 Positionen, 10 aktive Dateien je Position, 40 Dateien und 150 MiB je Nachforderung, 200 Uploads ueber die ganze Laufzeit — gezaehlt in der Transaktion NACH der Sperre.
  7. **Sperrreihenfolge ueberall Vorgang → Nachforderung → Position → Datei → `Document`.** Wer der Person eine Mail schickt, sperrt zuerst den Vorgang (`vorgangSperren`: `updateMany … status not EXPIRED`, 0 Treffer → 409 — so gewinnt ein gleichzeitiges `EXPIRED`), dann die Nachforderung (bedingt auf `LAUFEND`), und ERST DANN zaehlt er die Mail-Bremse und schreibt. HR-Aktionen und Lauf teilen die prozesslokale Sperre `laufendeUnterlagenAktionen` je `MODUL:vorgangId` (belegt → 409 „Gerade läuft eine andere Aktion …", der Lauf merkt vor und versucht am Ende einmal erneut). Die oeffentlichen Wege nehmen keine Prozesssperre, sperren aber den Kopf bedingt und pruefen danach Link, Nachforderung, Vorgang und Position erneut (N1) — ein gleichzeitiges Zurueckziehen oder „Entfällt" gewinnt sauber (410/409). Mails immer NACH dem Commit, Fehler nur loggen (Praefix, IDs, `error.code ?? error.name`).
  8. **Dateien: Typ aus den Bytes, Uebernahme per Hardlink mit Pruefsumme.** Der Typ kommt nur aus `erkenneDateityp` (PDF mit `%%EOF` am Ende, JPEG, PNG, WebP; sonst 415), nie aus `file.type` oder der Endung (`validateUpload` taugt dafuer nicht). Speichername `<dateiId>.<ext>` mit Endung des erkannten Typs; der bereinigte Anzeigename steht nur in der Datenbank, nie in Pfad, Mail, AuditLog oder Konsole. PDF-Merkmale (`/Encrypt`, aktive Inhalte) sind nur ein Hinweis fuer HR, nie ein Ablehnungsgrund. **Wurzeln je Operation, nie `uploads` als Ganzes** (darunter liegt `uploads/bem/`): lesen und loeschen nur unter `uploads/unterlagen/<nachforderungId>`, Ziel der Uebernahme nur unter `uploads/<vorgangId>` (`pfadInWurzeln`, `zielVerzeichnisPruefen`). Annehmen: erst verknuepfen (`fs.link`, bei EXDEV/EPERM Kopie; SHA-256-Vergleich, Abweichung → 409 „Datei verändert"), dann in EINER Transaktion umschalten (Position, je Datei ein `Document` mit `APPROVED`, `reviewedAt`/`reviewedById`, relativem `filePath`, AuditLog), erst nach dem Commit die Quelle loeschen — scheitert die Transaktion, das neue Ziel. Die Datei liegt so immer an mindestens einer Stelle, auf die eine Zeile zeigt; Reste findet der Lauf als Waise. Die Ruecknahme laeuft genauso rueckwaerts. HR sieht nur Dateien mit `uebermitteltAm`, Entwuerfe nie — beim Zurueckziehen und bei „Entfällt" werden sie sofort geloescht, eingereichte werden `VERWORFEN`.
  9. **Loeschen und taeglicher Lauf.** Zurueckgewiesene und verworfene Dateien 30 Tage nach dem Ereignis (`loeschenAb`), liegengebliebene Entwuerfe 30 Tage nach dem Linkende (erst bedingt die Zeile, dann die Datei — ein gleichzeitiges Uebermitteln gewinnt). Die Zeile bleibt als Nachweis (Name, SHA-256, Groesse, Begruendung); `dateiGeloeschtAm` nur bei „geloescht" oder „fehlte" (`dateiLoeschen`, drei Ergebnisse), bei „fehler" versucht es der naechste Lauf. Der Lauf je Nachforderung unter der Sperre des Vorgangs: Z2 (Regel 12), „vollständig" nachholen, Personen-Mail nachholen, Erinnerung (7 Tage vorher, am Fristtag), „Frist verstrichen" an HR, Aufraeumen samt Waisen (unter `uploads/unterlagen/` erst ab 24 h). Hoechstens EINE Mail an die Person je Nachforderung und Lauf; nach drei FAILED in Folge schickt der Lauf nichts mehr (SMTP-Bremse), raeumt aber weiter auf. **Merker bei SENT und SKIPPED, bei FAILED nicht**, bedingt auf den gelesenen Fristwert bzw. `vollstaendigSeit` — der Lauf ueberschreibt keine Friständerung. Faelligkeit steht in der Abfrage, Seiten zu 500 (N3). `?dryRun=1` plant dasselbe (`laufPlanen`), schreibt, mailt, loescht und sperrt aber nichts (`details[].status = "GEPLANT"`). Die Antwort traegt keine Personendaten (n8n speichert Ausfuehrungsdaten). Ohne eingeschalteten Lauf (Einstellungen → Automatische Läufe) gibt es weder Erinnerungen noch Loeschung; der **Lauf-Waechter** der Karte (`laufWaechter`) meldet dann „Der tägliche Lauf erreicht das Portal vermutlich nicht …" — fuer eine ausgebliebene VORAB-Erinnerung und ueberfaellige Loeschungen, nicht fuer den Fristtag (ein verpasster, auch ein von der SMTP-Bremse zurueckgehaltener, entfaellt still; sichtbar nur im Bericht des Laufs), und nicht, solange HR die Frist gestern oder heute gesetzt hat (der gestrige Lauf kannte sie nicht). Ein Probelauf (`dryRun`) erfuellt keine dieser Zusagen: echte Nachforderungen erst, wenn der Lauf scharf laeuft. Eingeplant wird der Lauf seit 09/2026 im Portal (Zeitplaner, Abschnitt „Automatische Läufe“), nicht mehr in n8n; Probelauf dort ueber den Schalter „als Probelauf“ bzw. „Probelauf jetzt“.
  10. **Oeffentliche API ohne Middleware.** Der Matcher in `src/middleware.ts` schliesst `api/unterlagen/` aus: Nur mit Middleware klont Next.js den Body, schneidet ihn bei 10 MiB ab und schreibt dabei die URL samt Token ins Log. Die Grenzen liegen deshalb in `unterlagen-upload.ts`, in verbindlicher Reihenfolge: IP-Bremse → Tokenformat (ohne Datenbank) → Content-Type → Content-Length → Link und Gueltigkeit → Bremse → Position → Kontingente → `leseBodyBegrenzt` (10 MiB, 413) → genau ein `datei` (≤ 9,5 MiB) → Typ → SHA-256 → Datei schreiben → Transaktion. Die JSON-Bodys (Gültig bis, Übermitteln) sind auf 64 KiB begrenzt. Jede Antwort geht durch `oeffentlicheAntwort()` (`no-store`, `nosniff`, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex`). Die SEITE `/unterlagen/[token]` bleibt unter der Middleware (CSP, `X-Frame-Options`) und bekommt dort `Referrer-Policy: no-referrer`; `robots.txt` sperrt `/unterlagen/`. Datenzuschnitt: Name, Einrichtung, Vorgangsnummer, Frist, Nachricht, Positionen mit eigenem Stand, die eigenen Entwuerfe, verantwortliche Stelle, Grenzen — nie Adresse, Name der HR-Kraft, Pruefsummen, Namen eingereichter Dateien. Keine IP wird gespeichert, auch nicht im AuditLog. **Datenschutzhinweise der Upload-Seite** (Art. 13, mit Art. 9): Wortlaut vom DSB (29.09.2026) in `DATENSCHUTZ_KONTAKT`/`DATENSCHUTZ_ABSCHNITTE` (`upload-seite.tsx`), aufklappbar in der Fusszeile (`<details>`). Den Verantwortlichen nennt die Seite wie der Fragebogen aus der Datenschutz-Einstellung des Mandanten (`verantwortlicheStelle`, Standard `DEFAULT_VERANTWORTLICHE_STELLE` = Christlicher Schulverein Minden e.V.); Kontakt-E-Mail und DSB gelten fuer alle Mandanten. Aenderungen am Wortlaut nur nach Ruecksprache mit dem DSB.
  11. **Datei-Route mit eigener CSP, Download-Route gehaertet.** `GET …/unterlagen/dateien/[dateiId]` (nur `HR_EDIT_ROLES`, AuditLog `UNTERLAGEN_DATEI_GEOEFFNET` je Oeffnen) liefert `inline`, Typ aus der Datenbank, `no-store`, `Cross-Origin-Resource-Policy: same-origin` und setzt ihre CSP SELBST: Bilder `sandbox`, PDFs `portalCsp()`. Die Middleware laesst die CSP fuer genau diesen Pfad weg (`routeSetztEigeneCsp`, `src/lib/content-security-policy.ts`), weil Next.js einen Kopf der Route nicht anhaengt, den die Middleware schon gesetzt hat. Ob die Browser das Inline-PDF unter der Portal-CSP anzeigen, klaert die Browserprobe nach dem Deploy (sonst PDFs als `attachment`). Die bestehende Download-Route `GET /api/onboarding/[id]/documents/[docId]` ist gehaertet, weil angenommene Nachweise nach Art. 9/10 DSGVO dort landen: nur `PORTAL_ROLES` (der n8n-Schluessel meldet sich als `SERVICE` an → 403), `canAccessProcess` mit 404 statt 403, Pfad nur unter `uploads/<onboardingId>`, `no-store`, Endung des Download-Namens aus `mimeType` (unbekannt → `application/octet-stream`, `.bin`), AuditLog `DOKUMENT_GEOEFFNET` bei sensiblen Arten.
  12. **`EXPIRED` und „unbefristet".** Bei `EXPIRED` (EP-3) sind Anlegen, Ergaenzen, Frist aendern, erneut senden und Zurueckweisen gesperrt (409 — jede verschickte eine Mail mit totem Link); Annehmen, Entfällt, Annahme zuruecknehmen und Zurueckziehen bleiben (sie sperren darum nur die Nachforderung, nicht den Vorgang; die Rueckfrage „Annahme zurücknehmen?" nennt dann vorher die Folge aus Z2, `dialog.ruecknahmeFolge`). Der Link antwortet 410, der Lauf mailt nichts. **Z2:** Der naechste Lauf zieht eine laufende Nachforderung eines `EXPIRED`-Vorgangs selbst zurueck (keine Mail, AuditLog `UNTERLAGEN_ZURUECKGEZOGEN` mit `details.grund = "VORGANG_EXPIRED"` ohne `userId`, im `dryRun` nur gezaehlt) — sonst liefe sie ewig und ihre ungeprueften Dateien wuerden nie geloescht. **Z3:** Die HR-Mails `dokument-ablauf-warnung`/`dokument-abgelaufen` verweisen nur mit `{{#nachforderung_moeglich}}` auf „Unterlagen nachfordern"; bei EXPIRED oder offenem Fragebogen steht `{{nachforderung_hinweis}}` (`onboardingNachforderungGesperrt`, dieselbe Regel wie `verfuegbar`), welche Mails hinausgehen, aendert sich nicht (Lauf bewusst ohne Statusfilter). Die Art im Satz ist `{{dokument_typ}}` — der Lauf mahnt Aufenthaltstitel und Arbeitserlaubnis je Art getrennt. **Z1:** `Document.unbefristet` — ein unbefristeter Nachweis (Niederlassungserlaubnis) erledigt die Art und verdraengt jedes datierte Dokument derselben Art (`nachweisLagen`: kein Warnbalken, keine Zeile „Frist fehlt"; `dokument-ablauf` ueberspringt ihn). Gesetzt beim Annehmen („Unbefristet (z. B. Niederlassungserlaubnis)") oder ueber den Knopf „Unbefristet" an der Dokumentenzeile (`PATCH …/documents/[docId]` mit `{ gueltigBis: null, unbefristet: true }`); ein Datum nimmt das Kennzeichen zurueck. `gueltigBis = null` allein heisst nur „noch nicht erfasst". In dieser Frist-Korrektur wird `EXPIRED` zu `APPROVED`, wenn `reviewedAt` gesetzt ist (das schreibt nur Paket 4), sonst wie bisher zu `UPLOADED`.
- **Protokoll:** AuditLog (`processType` des Moduls, im selben Commit wie die Aenderung), `details` nur mit IDs, Katalogschluesseln, Groessen, Typ, SHA-256, Fristen und Laengen — Nachricht, Begruendung, Hinweis und Notiz nur als Laenge, bei abweichender Adresse `adresseBestaetigt: true` statt der Adresse. Nie Token, Anzeigename, Adresse, IP. Beschriftungen in `UNTERLAGEN_AUDIT_LABELS` (ein Test verlangt eine je Aktion).
- **Prozesslokale Sperren und Bremsen** (Sperre je Vorgang, Laufsperre, SMTP-Bremse, oeffentliche Bremsen) tragen nur bei EINEM Container. Die Zustaende sichern Unique-Index und bedingte `updateMany`, die Mail-Bremse zaehlt aus der Datenbank — beim waagerechten Skalieren trotzdem durch eine gemeinsame Ablage ersetzen (wie Dokumentenpaket und Abteilungsaufgaben).
- **Stufe 2 = je Modul ein Baustein.** Offboarding, Verbeamtung, Vertragsverlaengerung, Elternzeit und Mutterschutz kommen ohne Umbau der Regeln (`unterlagen.ts`, Lauf, Mails). Je Modul: ein nullbarer FK samt Relation (Cascade) an `UnterlagenNachforderung`; dieselbe Spalte in `BEZUG_AUSWAHL` (`unterlagen-dienst.ts`, Typen ziehen mit) **und** in `KOPF_AUSWAHL` (`unterlagen-upload.ts`) — fehlt sie dort, liefert `vorgangIdAus` zur Laufzeit `null`, ohne tsc-Fehler (`KopfZeile` erfuellt den `Partial`-Bezug auch ohne sie); ein Eintrag in `UNTERLAGEN_MODULE` (`unterlagen.ts`) und der Anzeigename in `VORGANGSARTEN` (`unterlagen-mail.ts`; sonst steht still der Rohschluessel im Payload-Feld `vorgangsart`, das Vorlagen und Webhooks lesen); ein `UnterlagenModulBaustein` in `BAUSTEINE` (`unterlagen-dienst.ts`; `verfuegbar`, `vorgangSperren`, `auswahl`, `annahmePruefen`, `uebernehmen` — `neuerPfad: null` laesst die Datei bei der Nachforderung); ein Eintrag in `OEFFENTLICHE_MODULE` (`unterlagen-upload.ts`, schmales `select` der oeffentlichen Seite); ein Einstieg wie `unterlagenUebersichtLaden` fuer die Detailroute des Moduls; duenne HR-Routen unter der eigenen `apiBasis` und der Einbau der Karte. **Offener Folgeumbau:** `OEFFENTLICHE_MODULE` ist ein zweites Register neben `BAUSTEINE` — der Baustein soll ein `oeffentlichLaden(tx, id)` bekommen, dann entfallen das Register und die zweite Regel „EXPIRED = eingestellt" (Kommentar in `unterlagen-upload.ts`; bis dahin haelt ein Test beide gleich). Mutterschutz ueber `mitDetails` (keine Vorgangsnummer, keine Unterlagennamen in Mails). Ebenfalls Stufe 2: Listenspalte „Unterlagen" (E-6) und die Pseudonymisierung 12 Monate nach Abschluss (E-7).

## Automatische Läufe (Zeitplaner, 09/2026)

Alle taeglichen Laeufe (Erinnerungen, Fristen, Loeschungen) startet das Portal selbst — **n8n wird dafuer nicht mehr gebraucht** (Entscheidung 30.09.2026; Webhooks bleiben optionaler Zusatzkanal). Einstellungen → **Automatische Läufe** (nur `ADMIN_ROLES`): ein/aus, Uhrzeit (deutsche Zeit), „nur Mo–Fr“, Probelauf, „Bericht auch bei Erfolg“, „Jetzt ausführen“/„Probelauf jetzt“, Protokoll. Plan und Befund: `docs/module/betrieb/zeitplaner-plan.md`.

- **Wo die Regeln liegen:**
  - Rein, client-sicher, getestet (`src/__tests__/lib/zeitplaner.test.ts`): `src/lib/zeitplaner/katalog.ts` (`LAEUFE`: Name, Standardzeit, `kannProbelauf`, `loescht`, Vorlagen, Route), `faelligkeit.ts` (`laufFaellig`, `naechsterLauf`, `tagErledigtNachAenderung`, `laufAusgeblieben`), `bericht.ts` (Auswertung je Lauf, `berichtNoetig`, `berichtPayload`).
  - Server: `ausfuehren.ts` (`AUSFUEHRER`, `laufBeanspruchen`, `laufDurchfuehren`, `laufUeberRoute`), `dienst.ts` (Takt, Uebersicht, Einstellungen, Handstart), `uhr.ts` (Uhr + Zustand auf `globalThis`). Getestet in `zeitplaner-ausfuehren.test.ts`.
  - Die Laeufe selbst: `src/lib/laeufe/*.ts` (je eine Funktion `…Lauf(opts) → { status, body }`), dazu `unterlagenFristenLauf` (`unterlagen-lauf.ts`). Die Cron-Routen unter `/api/cron/*` sind duenn: `cronAnmeldungPruefen` + `laufUeberRoute`, Antwort 1:1 wie frueher.
  - Oberflaeche: `src/components/zeitplaner/automatische-laeufe-tab.tsx` — rechnet nichts selbst, alles kommt fertig aus `uebersichtLaden`. Routen `/api/settings/automatische-laeufe[/[schluessel][/ausfuehren]]` (`adminHandler`).
- **Acht Regeln, die beim Aendern gelten muessen:**
  1. **Die Uhr ruft eine Route, nie die Laeufe direkt.** `src/instrumentation.ts` startet `uhr.ts` (nur Node-Runtime, nie im Build); die Uhr ruft jede Minute `POST /api/zeitplaner/takt` im SELBEN Prozess. Next.js buendelt die Instrumentation getrennt — ein direkter Aufruf gaebe jedes Modul zweimal (zweiter PrismaClient, zweite prozesslokale Sperren wie `laufendeUnterlagenAktionen`). `uhr.ts` importiert deshalb nichts aus dem Portal, auch nicht `crypto` (Edge-Buendel; Web Crypto). Die Takt-Route prueft ein zufaelliges Geheimnis, das nur im Speicher liegt (`x-zeitplaner-token`, sonst 404) — von aussen nicht aufrufbar, keine Umgebungsvariable noetig.
  2. **Eine Tuer fuer alle Ausloeser.** Takt, Knopf und Cron-Route gehen durch `laufBeanspruchen` → `laufDurchfuehren`: Anspruch per bedingtem `updateMany` auf `AutomatischerLauf` (frei = `laeuftSeit` leer oder aelter als 2 h; beim Zeitplan zusaetzlich aktiv und `tagErledigt < heute`), 0 Treffer → 409 bzw. kein Start. `tagErledigt` (Berliner Kalendertag als String) setzt jeder Lauf des Zeitplans — **auch ein eingeplanter Probelauf** (sonst startete ihn jeder Takt neu: jede Minute Lauf + Berichtsmail) — sowie jeder echte Lauf von Hand/Route; nur ein Probelauf von Hand/Route nicht. Wer den Anspruch nimmt, schliesst noch offene `LAEUFT`-Zeilen desselben Laufs als `FEHLER`/`ABGEBROCHEN` (Neustart mitten im Lauf); die Oberflaeche wertet eine Sperre aelter als 2 h als verwaist (Karte nicht gesperrt, Zeile „abgebrochen“). Freigabe im `finally`, bedingt auf den eigenen Zeitstempel. Fehlende Einstellungszeilen legt `einstellungenLaden` nur an, wenn wirklich welche fehlen. Wer einen neuen Lauf baut, traegt ihn in `LAEUFE` UND `AUSFUEHRER` ein (ein Test haelt beide gleich) und laesst seine Route durch `laufUeberRoute` gehen.
  3. **Neue Laeufe kommen AUS.** `laeufeSicherstellen` legt fehlende Zeilen mit `aktiv = false` an und aendert vorhandene nie. Sechs der Laeufe (Verbeamtung, Vertragsende, Elternzeit, BEM-Fristen, BEM- und Dokumente-Aufbewahrung) waren vor dem Zeitplaner nie eingeplant — der erste Lauf verschickt alles Faellige auf einmal bzw. loescht.
  4. **Loeschlaeufe erst nach einem Probelauf scharf** (`scharfGesperrt` → 409 `PROBELAUF_FEHLT`), serverseitig geprueft beim Einschalten, beim Abwaehlen von „als Probelauf“ an einem eingeschalteten Lauf und bei „Jetzt ausführen“ — die Oberflaeche sperrt nur mit (`probelaufFehlt`). Als Probelauf geht immer. Jeder Lauf mit `loescht` braucht `kannProbelauf` (Test). `bem-aufbewahrung` hat dafuer `dryRun` bekommen.
  5. **Kein ueberraschender Sofortlauf.** Einschalten oder Uhrzeit verschieben nach der Uhrzeit legt `tagErledigt` auf heute (erster Lauf morgen), davor mindestens auf gestern (Lauf heute, kein Fehlalarm des Waechters). Nachholen nur am selben Tag (Container war um 08:00 aus); ausgefallene Vortage holt der naechste Lauf zustandsbasiert nach. Sommerzeit: `berlinerZeit` ueber `Intl`, eine fehlende Uhrzeit (02:30 im Maerz) laeuft ab 03:00, eine doppelte nur einmal.
  6. **Protokoll und Bericht ohne Personendaten.** `AutomatischerLaufProtokoll` (90 Tage, Lauf „wartung“) und die Berichtsmail tragen nur Zaehler, zusammengefasste Schritte („2 × Abteilung · Warnung · versendet“) und `fehlerKennung` — nie Namen, Adressen, Vorgangsnummern, Tokens. Berichtsmail = Event `automatischer-lauf-bericht` ueber `triggerWebhooks` (darf an Webhooks, weil ohne Personendaten), An `{{hr_postfach}}` (= `SmtpConfig.replyToEmail`), nur bei Problemen, Fehlern, Probelaeufen und — Schalter je Lauf — nach versendeten Mails. Merker als Zeichenkette (`"ja"`/`""`). Die Auswertung liest die Antwort jedes Laufs ueber `AntwortLeser`: Fehlt ein erwartetes Feld (etwa nach einer Umbenennung im Lauf), wird der Lauf „bitte prüfen“ mit Zeile „Antwort unvollständig – es fehlen …“ — nie still 0. Wer die Antwort eines Laufs aendert, passt `AUSWERTER` in `bericht.ts` mit an.
  7. **Dritte Dispatcher-Ausnahme: `bem-frist-erinnerung`.** `bemFristenLauf` schickt je freigegebenem Beauftragtem `sendEventEmail(BEM_FRIST_EVENT, …, { overrideTo: adr })`, nie ueber `triggerWebhooks` — Empfaenger sind nur die im Fall freigegebenen Beauftragten, ein Verteiler in der Vorlage greift nie, Fallnummer und Fristart gehoeren an keine Webhook-URL. Der Betreff nennt keine Fallnummer (`betreffOhne`), weil er 90 Tage im allgemeinen Versandprotokoll steht. `logBemKommunikation` bleibt. Die Stufe (`letzteSeverity`) wird ERST NACH dem Versand gesetzt: bei SENT (mindestens ein Beauftragter) und SKIPPED ja, bei FAILED und ohne freigegebene Beauftragte nein — der naechste Lauf versucht es erneut (`bem-fristen-lauf.test.ts`). `ereignis-liste.test.ts` haelt Quelltext und `EVENTS_OHNE_WEBHOOK` gleich.
  8. **Waechter statt n8n-Fehlermail.** `laufAusgeblieben`: aktiv, aber der letzte Termin (plus 60 min Karenz, Werktage beachtet) nicht erledigt → rote Zeile im Reiter; steht die Uhr ganz, bewegt sich `tagErledigt` nicht mehr. `GET /api/health` meldet `zeitplaner.uhrAktiv`/`letzterTakt`. Steht der ganze Container, kann das Portal sich nicht selbst melden — dafuer den Health-Check von aussen ueberwachen.
- **Mails der Laeufe:** Verbeamtung (`psi-deadline-warning`) und Elternzeit (`elternzeit-frist-eskaliert`) warten das Mailergebnis jetzt ab (frueher fire-and-forget), damit der Bericht es melden kann; die Antwort traegt dazu `mailStatus` bzw. `mailsFehler`/`mailsUebersprungen`.
- **Prozesslokal bleibt nur die Uhr** (je Container eine). Sperre und Tagesmerker liegen in der Datenbank und tragen auch beim waagerechten Skalieren; die prozesslokalen Sperren einzelner Laeufe gelten wie bisher.

- **Prozessleiste und Reiter (Pilot Vertragsende, Tag 2).** Beide stehen auf `/ui-muster` (eigene Muster-Dateien `prozessleiste-muster.tsx`, `reiter-muster.tsx`; die Lagen der Leiste kommen dort aus dem echten Vertragsende-Adapter mit festem `JETZT`). **`Prozessleiste`** (`prozessleiste.tsx`): zeichnet einen `ProzessStand`, kennt kein Modul und ruft nichts; `aktion`/`nebenAktion` bekommt sie als fertige Knöpfe (die Seite gibt sie nur mit Bearbeitungsrecht), gezeichnet werden sie nur MIT `jetztDran`. Schritte als `ol` mit ausdrücklichem `role="list"` (Tailwind nimmt die Listenzeichen, Safari/VoiceOver sagt die Liste sonst nicht an); der Punkt ist Zierde, jeder Zustand hat ein Wort für Screenreader (`SCHRITT_WORT`; in einem beendeten Ablauf „nicht erreicht“ statt „kommt noch“) und ist ohne Farbe erkennbar (Haken · Hof und fetter Titel · Nummer · gestrichelter Rand und durchgestrichener Titel). Der Rand des übersprungenen Punkts TRÄGT Bedeutung (`ink-2`, 3:1), der des kommenden ist Zierde (`ink-3`). Ein Schritt mit `reiter` ist nur mit `onReiter` ein Knopf. Dringlichkeit steht als `Statuspille` mit Wort („Kritisch“, „Frist naht“) neben der Frist; wer dran ist, über `BEI_NAME`, das Ende über `ENDE_NAME` (beide in `prozess-stand.ts` — der Baustein führt keine Namen). Unter 640 px: Punkte in einer Zeile, Titel/Unterzeile/anderer Weg `max-sm:sr-only` (nie `hidden`), darunter `schrittKurzform`. Kein `sticky` (P-F6). **`Reiter`/`ReiterInhalt`** (`reiter.tsx`, Radix Tabs — das Gegenstück zum `Segment`): gesteuert über `wert`/`onWechsel`, liest nichts aus der Adresse; ein unbekannter `wert` fällt auf den ersten Reiter; nur der Inhalt des gewählten Reiters steht im DOM (er lädt mit dem Wechsel, Eingaben darin gehen beim Wegwechseln verloren). Drei Dinge macht der Baustein ANDERS als Radix, jeweils mit Test: `onWechsel` läuft je Klick genau einmal (Radix meldet bei `mousedown` und beim `focus` danach — mit dem Reiter in der Adresse wären das zwei Navigationen); der Halt der Tab-Taste liegt immer auf dem GEWÄHLTEN Reiter (`tabIndex`, sonst schaltet Umschalt+Tab nach einem Wechsel von außen zurück); Bild-auf/Bild-ab rollen die Seite, statt zum ersten/letzten Reiter zu springen. Der Strich des gewählten Reiters ist ein echter Rand, die übrigen tragen gar keinen (Windows-Kontrastmodus); die Leiste rollt am Handy waagerecht und holt den gewählten Reiter in den sichtbaren Teil. Radix wählt bei `mousedown`, nicht bei `click` — Tests spielen die ganze Folge einer Maustaste.
- **Hinweis und Textfeld (Pilot Vertragsende, Tag 3, vor dem Prototyp-Tag vorgezogen).** Beide stehen auf `/ui-muster` (`hinweis-muster.tsx`, `textfeld-muster.tsx`), Regeln in `ui-hinweis-textfeld.test.tsx`, Farben in `ui-kontrast.test.ts`. **`Hinweis`** (`hinweis.tsx`): ein Kasten für EINE Aussage über der Arbeit, `ton` `critical`/`wait`/`info` (kein `ok` — Erledigtes braucht keinen Kasten), `titel` ist Pflicht (leer → zeichnet nichts), `children` ein, zwei Sätze, höchstens ein Knopf (`aktion`). Jeder Ton hat ein eigenes Standardsymbol (Form, nicht nur Farbe; `symbol` ersetzt es), Emojis nie. Angesagt wird nur, was NACH dem Laden erscheint: `ansagen` macht einen `critical`-Hinweis zu `role="alert"`; sonst ist er ein Bereich mit Überschrift (`section` + `aria-labelledby`, Vorgabe `h2`, tiefer über `ebene`) — die Seite entscheidet das, der Baustein rät es nicht. Text in `ink`, nicht `ink-2` (auf `critical-soft` über dem Seitengrund nur 4,49:1); durchsichtiger Rand für den Kontrastmodus. **`Textfeld`** (`textfeld.tsx`): sichtbare Beschriftung ist Pflicht (nie nur ein Platzhalter), nur `text`/`email`/`tel`/`url` (Datum und Auswahl kommen mit ihrem ersten Aufrufer). `hilfe` und `fehler` hängen über `aria-describedby` am Feld (erst Hilfe, dann Fehler, dann eine eigene `aria-describedby` des Aufrufers); ein Fehler setzt `aria-invalid`, färbt den Rand `critical` und steht als Text darunter, ein leerer Fehler ist keiner. Den Fokus auf einen neuen Fehler legt der Dialog, nicht das Feld. Rand `ink-2` (3:1 für Bedienelemente; `hairline` wäre als Grenze nicht zu sehen), Platzhalter `ink-2`. `className` geht an die Hülle, alles andere (`id`, `value`, `ref`, `data-autofokus` …) an das Feld. **`Textverweis`** (`textverweis.tsx`, 07.10.2026): ein Verweis im laufenden Text (Satz, Dialog, schmale Zeile) — ein Verweis FÜHRT woandershin, ein Knopf HANDELT; intern (`href` mit genau einem führenden „/“) über `next/link`, sonst (`mailto:`, `https:`, `//host`) ein `<a>`; unterstrichen in `ink`, Fokusring der Bausteine, keine eigene Farbtabelle. Regeln in `ui-textverweis.test.tsx`. Ein Verweis, der wie ein Knopf aussehen soll, bleibt `<Button asChild><Link …/></Button>`.
- **Neue Detailseite Vertragsende und Vorschau-Schalter (Pilot, Tag 3–5, auf Wunsch des Projektverantwortlichen VOR dem Prototyp-Tag gebaut).** Alles neben der Seite in `src/app/(portal)/vorgaenge/vertragsende/[id]/`: `page.tsx` (Weiche), `ansicht-schalter.tsx`, `detail.tsx`, `reiter-uebersicht.tsx`, `reiter-vertragsdaten.tsx`, `reiter-dokumente.tsx`, `dialoge.tsx`, `typen.ts` (Datentyp der GET-Antwort, Reiter samt `reiterAusSuche`, Texte der Handlungen, `anzeigeName`, `MAV_AUSWAHL`), `aufrufe.ts`; Hinweise in `src/lib/prozess/vertragsende-hinweise.ts`; die alte Ansicht bleibt Zeile für Zeile unverändert unter `(portal)/dashboard/contract-end/[id]/`. **Schalter:** Cookie `ansicht-vertragsende` nur über `src/lib/ansicht.ts`; die Seite liest ihn auf dem SERVER und liefert genau eine Ansicht; Vorgabe alt, nur der Wert „neu“ schaltet; Umschalten setzt/löscht den Cookie (`Secure` nur auf https) und lädt über `seiteNeuLaden` ganz neu; „Rückmeldung geben“ ist ein `mailto:` an `personalbuchhaltung@fes-minden.de`. Das Bearbeitungsrecht rechnet `page.tsx` (`HR_EDIT_ROLES`) — `permissions.ts` zieht Prisma mit und gehört nie in Client-Code. Die neue Ansicht steht in `<Suspense>` (`useSearchParams`). **Regeln der Ansicht:** Sie rechnet nichts selbst (Adapter, Hinweise, Aufrufe); jede Handlung hat GENAU einen Ort (Knopf in „Jetzt dran“ oder Menüpunkt); `aufrufe.ts` hält DIESELBEN Aufrufe wie die alte Ansicht (ein Test vergleicht mit deren Quelltext), neu ist nur „stornieren“ (P-F2). Knöpfe, Menü, „Stand setzen …“ und Dialoge nur bei `handlungenFrei` = Bearbeitungsrecht UND aktueller Stand: Scheitert das Neuladen nach einer Handlung, bleibt der alte Stand lesbar, aber gesperrt, mit dem angesagten Hinweis „Die Ansicht ist nicht aktuell“ und „Neu laden“. Nach jeder Handlung ist die Seite `beschaeftigt`, bis der neue Stand da ist (Knöpfe `aria-disabled`, Menüpunkte gesperrt, reine Verweise frei) — sonst schickte ein zweiter Klick auf dem alten Stand z. B. eine zweite Anfrage. Der Wächter liest eine Ref (`handelnGesperrt`), keinen Closure-Wert: Der Seitenkopf führt einen Menüpunkt erst NACH dem Schließen mit dem Handler aus dem Moment der Wahl aus. Fokus: Verschwindet der Auslöser mit dem neuen Stand, bekommt der Seitentitel den Fokus (Effekt an einem Zähler der abgeschlossenen Ladevorgänge, `ladeStand`). Der Reiter steht in der Adresse (`replaceState`, `?tab=` mit deutschen Namen und den Schlüsseln der alten Ansicht); den Startwert liest die Ansicht aus `useSearchParams`, nicht aus einer Eigenschaft der Seite (Zurück/Vor). Die Reiter Dokumente und E-Mails tragen eine `sr-only`-`h2` (die bestehenden Karten bringen `h3` mit). Dialogtexte sagen nur, was die Route wirklich tut: „Anfrage neu senden“ verwirft KEINE Vertragsdaten (die alte Ansicht behauptete es; `/supervisor-link` legt sie per `upsert` unverändert an); „Der Link wird ungültig“ nur bei `fuehrungskraftKannAntworten` (Adapter). Ein Formatfehler der Adresse steht nur im Dialogfuß, das Feld trägt `aria-invalid`; eine unveränderte Wiederholung wird über `flushSync` (leeren, dann setzen) erneut angesagt. **Versandergebnis (seit 10/2026):** `/supervisor-link` und `/reminder` melden `mailStatus` (Erfolg SENT oder WEBHOOK; nicht zugestellt FAILED mit 502, SKIPPED mit 409); `aufrufen` reicht ihn in BEIDEN Ergebnissen durch (`mailStatusAus`). Ein Fehler MIT `mailStatus` heißt „gespeichert, nur die Mail ging nicht hinaus“ (neuer Link gespeichert, ein früherer tot): Der Anfrage-Dialog bleibt offen mit der Meldung der Route, die Seite lädt dahinter still neu (`onGeaendert` → `dialogGeaendert`, ohne `beschaeftigt`, damit ein zweiter Versuch im Dialog geht); schließt HR den Dialog vor dem Ende dieses Ladens, wartet die Seite darauf (`dialogAbbrechen`; `wartetAufStand` ist ein Zähler, weil sich zwei Ladevorgänge überlappen können). Die Rückfrage sagt ab diesem Fehlschlag „der bisherige gilt bereits nicht mehr“ — zugleich mit der Meldung, nicht mit dem neu geladenen Stand. Die Erinnerung zeigt den Fehler der Route als `toast.fehler` und lädt neu. Bei WEBHOOK sagt die Meldung „an den Webhook weitergegeben“, nie „gesendet“ (`anfrageMeldung`, `erinnerungMeldung`). Die Testumgebung (Dev und Docker) hat bewusst keinen Mailserver: Anfrage und Erinnerung scheitern dort immer mit „SMTP ist nicht konfiguriert …“ — der Prototyp-Tag prüft genau diese Meldung (`prototyp-tag-leitfaden.md`, Aufgaben 4 und 5). Hinweise über allen Reitern: Vorstand-Warnung nur bei entschiedener Übernahme und laufendem Vorgang (das Formular speichert den Vermerk schon beim Zwischenspeichern), Kettenbefristung nur bei laufendem Vorgang, „weitere Einstellungen“ immer. `GET /api/contract-end/[id]` liefert zusätzlich `renewalData.betriebsstaetteName` (Name zu `betriebsstaetteOrgId`; das Freitextfeld trägt nur Altbestand) — rein additiv. **Testdaten:** `scripts/vertragsende-testdaten.js` legt je Lage einen fiktiven Vorgang an (VE-…-T01 bis T10, Offboarding OFF-…-T07); es löscht NUR Vorgänge mit `@beispiel.invalid` UND T-Nummer samt ihrer abhängigen Zeilen ohne Fremdschlüssel (erzeugte Dokumente, Paketnachweise, individuelle Mails, Mailprotokoll; Dateien nur unter `uploads/brief-vorlagen-generiert` bzw. `uploads/individuelle-mails`), Host nur localhost/127.0.0.1 oder genau `TESTDATEN_HOST_ERLAUBT` (Docker: `db`).
